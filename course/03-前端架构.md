# 03 · 前端架构

## 3.1 为什么不用框架

天启前端是纯 HTML + 原生 JS，没有 React/Vue，也没有打包构建流程。每个页面（`memos.html`、
`harness.html`……）是独立的入口，通过 `<script src="...">` 按固定顺序加载脚本。

> **大白话**：不是所有前端都需要框架。框架解决的核心问题是"复杂交互状态下的声明式 UI 更新"，
> 而这个项目大部分页面是"服务端数据 → 渲染列表 → 局部更新"，用 `innerHTML`/`appendChild` 手写
> 完全可以覆盟，还省掉了构建工具链的维护成本。Harness 页面（三栏实时更新）复杂度更高一些，
> 但也是靠"状态对象 + 重新渲染函数"这种朴素模式解决的（后面 [12](12-harness-HTTP接口与前端联调.md) 会细讲）。

## 3.2 核心脚本加载顺序：`utils → auth → api → ui`

这四个文件是每个页面的公共底座，**顺序不能乱**，因为存在依赖关系：

1. **`utils.js`**：纯工具函数（HTML 转义 `escHtml`、日期格式化、骨架屏、toast 提示），零依赖，
   挂到 `window` 上供其他脚本直接用。
2. **`auth.js`**：`Auth` 对象管理登录状态。关键设计——`Auth.token()` **不返回真正的 JWT**，
   而是返回一个哨兵字符串 `'__cookie__'`（当用户已登录时）：

   ```js
   token() { return this._user ? '__cookie__' : ''; }
   ```

   > **严谨定义**：哨兵值（Sentinel Value）是一个不携带真实业务含义、仅用于表示"某种状态"的特殊值，
   > 目的是复用已有的条件判断语法而不暴露真实数据。
   >
   > **大白话**：JWT 是 `HttpOnly` Cookie，JS 从代码层面**读不到**它（这是故意的，防 XSS 偷 token）。
   > 但前端代码里到处都要写 `if (Auth.token()) { ... }` 这种"判断是否登录"的逻辑，总不能因为读不到
   > token 就把这些判断全改写。于是让 `token()` 返回一个"看起来像 token，其实只是个开关"的假值——
   > 代码读起来还是自然的 `if (Auth.token())`，但它根本不是凭证，泄露出去也没有任何危害。

   `Auth.csrfToken()` 则是真的从 `document.cookie` 里读 `mw_csrf`（这个 Cookie 故意不是 HttpOnly，
   前端必须读得到才能塞进请求头）。

3. **`api.js`**：`apiFetch()` 是唯一和后端对话的函数——自动加 `Content-Type`（除非是 `FormData`，
   要保留浏览器自动生成的 multipart 边界）、非安全方法自动带上 `X-CSRF-Token`、始终
   `credentials: 'include'`（带上 Cookie）、非 2xx 状态码抛出携带服务端错误信息的 `Error`。
   **它只返回解析好的 JSON**——这个限制很关键，直接导致了下一条。
4. **`ui.js`**：往每个页面注入悬浮组件（AI 精灵、音乐播放器），处理导航栏等通用 UI 逻辑。

## 3.3 流式接口为什么不能用 `apiFetch`

Harness 对话流、AI 精灵聊天流都是 SSE（Server-Sent Events），响应是"一边生成一边吐字节流"，
而 `apiFetch()` 设计成"等响应完整返回后解析 JSON"，天生不兼容流式场景。所以这些地方绕开
`apiFetch`，直接用裸 `fetch()`：

```js
fetch('/api' + url, {
  credentials: 'include',
  headers: { 'X-CSRF-Token': Auth.csrfToken() },
  ...
})
```

手动把 `apiFetch` 原本自动做的两件事（带 Cookie、带 CSRF 头）补回来，然后自己用
`response.body.getReader()` 逐块读取、按 `\n\n` 切分 SSE 帧、按 `data: ` 前缀（注意这个空格，见
[02](02-后端分层架构.md) 里 `core/sse.py` 的说明）解析出 JSON。

> **面试话术**：这是一个"通用封装 vs 特殊场景"的典型权衡——不是每个网络请求都套用同一个封装函数
> 就是"更工程化"，流式响应有它自己的消费模型，硬套统一封装反而会增加理解成本。知道什么时候该
> "破例"，也是工程判断力的一部分。

## 3.4 三个可拖拽悬浮组件

AI 精灵、音乐播放器、时钟，共享同一套拖拽/缩放引擎 `floating-panel.js`：

- **拖拽起始阈值 4px**：鼠标按下后移动超过 4 像素才判定为"拖拽"，否则判定为"点击"——如果没有这个
  阈值，音乐播放器的"播放"按钮会因为鼠标按下瞬间的微小抖动被误判成拖拽，导致点击失效。
- **定位方式固定用 `left`/`top`，绝不用 `transform`**：因为精灵组件自己有"待机呼吸"动画、
  时钟有"指针跳动"动画，这些动画本身就用 `transform` 实现。如果拖拽逻辑也去改 `transform`，
  两者会互相覆盖打架。用 `left`/`top` 定位、`transform` 留给动画专用，是"同一个 CSS 属性不能
  身兼两职"这个坑的实际解法。
- 每个组件通过 `onResize(width, height)` 回调自己决定"变大了该怎么办"（3D 精灵是重新计算渲染分辨率，
  文本类面板是重新排版）——引擎本身不关心"缩放意味着什么"，只负责测量和分发事件，这是一个小型的
  策略模式应用。
- 布局状态存在 `localStorage`，页面加载和窗口 resize 时都会做一次"夹回可视区域内"的校正，避免拖到
  屏幕外后找不到。

## 3.5 精灵组件的"无文字气泡"设计与坐标计算细节

AI 精灵「天启」没有传统的对话气泡，靠眼睛形状、瞳色、光晕（`MOODS` 对象里定义的几种状态）来表达
情绪。这背后有个真实踩过的坑：早期版本有一个"悬浮问候语"气泡，靠计时器控制显示/隐藏，结果和鼠标悬停
状态的计时器产生竞态（谁先谁后不确定），有时候气泡卡住不消失。最终选择直接删掉这个交互，用更简单的
视觉状态代替——**有时候修 Bug 最好的办法是移除引入这个 Bug 的功能，而不是加更多状态去堵漏洞**。

另一个细节：对话框展开动画用了 `transform: scale()`，如果用 `getBoundingClientRect()` 测量对话框
尺寸，动画播放过程中测到的是"正在缩放中的临时尺寸"，不是最终尺寸。改用 `offsetWidth`/`offsetHeight`
（不受 CSS transform 影响的布局尺寸）来定位。同时对话框是"从几乎空白开始、随着流式回复变长"的，
所以还挂了一个 `ResizeObserver` 持续重新定位——如果只在打开那一刻定位一次，回复变长后底部内容和
输入框会被推到可视区域外面。

> **大白话**：这两个坑本质是同一类问题——"测量时机不对"。用 `getBoundingClientRect()` 或者只测量
> 一次，都是"假设尺寸是静态的"，但动画和流式内容让尺寸变成了"动态的"。这是前端里一个容易被忽略但
> 很常见的类别的 bug：忘记某个值会随时间变化。

## 3.6 页面滚动劫持与悬浮层的冲突

首页 `index.js` 用滚轮事件驱动"时间裂隙"分屏动画（`wheel`/`keydown`/`touchstart` 都被接管，用来
控制页面切换而不是普通滚动）。如果不做任何处理，用户在 AI 精灵回复框里滚动查看长文本时，滚轮事件会
同时被首页的全局监听器捕获，导致回复框内容和背后的整个页面一起滚动/翻页。解决方式是维护一个
`OVERLAYS` 白名单，所有全局滚动/按键事件处理器在派发前先检查事件是否发生在某个悬浮层内，是则直接放行、
不做劫持。

## 3.7 THREE.js 精灵渲染的降级策略

`new THREE.WebGLRenderer()` 不仅在 THREE.js 库没加载成功时会抛异常，**在浏览器/显卡不支持创建
WebGL 上下文时也会抛异常**（比如某些虚拟机、被禁用硬件加速的环境）。两种情况都会 fallback 到
`useFallbackSprite()`（一个更简单的 2D 精灵）。这里有个必须小心处理的细节：如果这个 fallback 函数
本身没有被 try/catch 包住就抛了异常，会连带把点击处理器和 `toggleSpriteChat` 函数一起带崩，
导致整个 AI 助手在这类环境下完全不可用、且没有任何错误提示——**一个兜底方案本身如果不够健壮，
就不是真正的兜底**。

## 3.8 小结

前端部分的技术含金量不如 Harness 高，但它体现的是另一种工程能力——**在没有框架托底的情况下，
靠约定（加载顺序、命名规范、状态对象+渲染函数模式）维持代码的可维护性**。面试被问到"为什么不用
框架"时，能说清楚"因为交互复杂度没到需要框架解决的程度"，比盲目追新技术栈更能体现判断力。
