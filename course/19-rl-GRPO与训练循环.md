# 19 · GRPO 与训练循环

前四章把环境、数据、奖励、分词都准备好了。这一章讲算法本身，以及把它们串成一个
能跑的循环时那些「顺序上的错」。

---

## 19.1 GRPO：为什么不需要 critic

> **严谨定义**：策略梯度需要一个基线（baseline）来降低方差。PPO 用一个学出来的
> value network 当基线。GRPO（Group Relative Policy Optimization）改用
> **同一道题的 G 条 rollout 的平均奖励**当基线。
>
> **大白话**：PPO 请了个教练，专门预测「这道题一般能考多少分」，然后看你超没超过预测。
> GRPO 不请教练——直接让你把同一道题做 8 遍，**用你自己这 8 遍的平均分当参照**。
> 省掉了训练、调参和怀疑一个额外模型。

实现是十几行（`rl/train/grpo.py::group_advantages`）：

```python
for gid in torch.unique(group_ids):
    group = rewards[group_ids == gid]
    std = group.std(unbiased=False)
    if std < min_group_std:            # 退化组，见下
        keep[members] = False
        continue
    advantages[members] = (group - group.mean()) / (std + eps)
```

### 退化组：最重要的健康指标

如果一道题的 G 条 rollout 奖励**全一样**（全对或全错），组内标准差为 0，
每条的 advantage **精确为 0**，这一组贡献的梯度**精确为零**——但它照样花掉了 G 条完整 rollout。

> **大白话**：8 条轨迹，每条十几步，全跑完了，梯度是 0。钱和时间都花了，什么也没学到。

这就是 `all_zero_groups` 这个指标（`rl/train/metrics.py`）存在的理由，
也是它在告警表里排第一的理由：

> **reward 曲线看不出这件事**。reward 走平，loss 正常，而**损失函数里一切正常**。

配套的两个动作：退化组在 loss 里被跳过（不是乘零——乘零还会稀释 token 级分母），
以及冷启动 SFT（19.5）。

## 19.2 token 级归一化：一个可以被算出来的选择

这是 GRPO 实现里最容易含糊过去、但**能用一个数字说清**的决定。

两种写法：

- **按序列取平均**：每条轨迹算一个 loss，再对轨迹取平均。
- **token 级归一化**：把 batch 里所有未 mask 的 token 的 loss 加起来，
  除以**它们的总数**（`sum / batch 内 mask token 总数`）。

上一章量到：轨迹长 1,800–3,300 token，**可训练部分只占 7–12%**，而且长度差异很大。

实测（`rl/checks/rl_check.py` 里钉死的用例）：

```
一条 5 token 的轨迹（advantage +1）+ 一条 1 token 的轨迹（advantage −1）
  token 级归一化 : -0.667
  按序列取平均   : +0.000      ← 两条完全抵消
```

> **大白话**：按序列平均，一条 5 个 token 的轨迹和一条 1 个 token 的轨迹**权重一样**。
> 于是上面这个例子里，一个「做对了很多」和一个「做错了一点」**恰好抵消成 0**——
> 明明该往正方向走。

多轮场景下这个偏差是**系统性的**：它一直在低估长轨迹，
而长程行为正是这个环境要训练的东西。所以选 token 级（DAPO 的做法）。

> 面试时这条可以直接给数字：`-0.667 vs +0.000`。
> 能算出来的选择，比「我看论文这么写的」强一个量级。

## 19.3 `logp_old` 必须在采样时记录

```python
ratio = torch.exp(logp - logp_old)
```

`logp_old` 是**采样那一刻**策略给出的对数概率。如果事后用当前策略重算：

> **大白话**：你就得到了当前策略自己的数字，于是 `ratio` 恒等于 1，裁剪永远不触发。
> 现象是「clip_fraction 一直是 0」——**看起来还像「训练很稳」**。

所以 `PolicyAdapter` 在请求生成时就带回 `logprobs`（第 18 章的方案 B 顺便解决了这件事），
`clip_fraction ≈ 0` 被写进告警表（`metrics.py::warnings`）。

### 一个并发带来的对位问题

`logp_old` 要放到序列里正确的位置上。而并发 rollout 的**完成顺序是乱的**，
所以不能按记录顺序配对：

> **大白话**：按顺序配，就会把一次生成的 log-prob 配到另一次生成的 token 上。
> ratio 变成垃圾，loss 依然有限，没有任何报错。

做法是**按 prompt 前缀匹配**：每条记录都带着它当时的 `prompt_token_ids`，
而一个 assistant span 的 prompt 恰好就是 `token_ids[:span.start]`
（`rl/train/pack.py::_place_logprobs`）。

匹配不上的怎么办？**整条丢弃**，让训练回退到冻结前向（那条样本的 ratio 恰好为 1）：

> 部分覆盖是不能用的——同一条序列里一些 span 的 ratio 是真的、一些是 1，
> 两者权重不可比。**宁可退化成「第一步 on-policy」，也不要真假混用。**

配套的工程决定：`engine.run_many` 收的是**策略工厂**而不是适配器实例，
每个 episode 建一个自己的适配器，这样生成记录天然归属明确。
（我一开始想用鸭子类型区分「实例」和「工厂」，结果**适配器的类也有 `stream` 属性**，
于是类本身被当成适配器传了下去。改成显式的 `engine.shared(adapter)` 之后，
立刻暴露出一处过时调用点——这就是显式的好处。）

## 19.4 一步训练的七件事

`rl/train/loop.py::run()`：

```
1. 从课程池的活跃子集采题
2. 每题 rollout G 条（打的是当前 adapter）
3. 验证器打分，结果回灌课程池
4. 打包成带 loss mask 的 token 序列
5. 组内归一化成 advantage，退化组跳过
6. 一步裁剪的 token 级损失
7. 存 LoRA adapter 并换进服务
```

**第七步是最贵的静默故障。** 漏掉它：训练照常进行、loss 照常下降，
但**第 1 步之后的每一条 rollout 都来自基座模型**——数据变成离策略的，
而 reward 曲线不会动，你会以为是算法不行。

所以 `lora_serve.check_runtime_lora()` 在循环开始**之前**就问一次服务器：
没开 `VLLM_ALLOW_RUNTIME_LORA_UPDATING=1` 的话热插拔端点返回 404，直接报错退出。

### 需要 GPU 的只有三个 hook

`TrainHooks` 只有三个方法：`forward_backward` / `publish` / `evaluate`。
采样、课程更新、指标累积、告警**全是纯 Python**，所以在没有卡的机器上用 stub
就能把编排逻辑完整跑一遍。自检里正是这么验的：

```
6 步 · forward_backward 11 次 · 换权重 3 次 · 评测 2 次 · 退化批次被跳过 · 告警 5 条
```

注意 `forward_backward 11 次` 而不是 12——有一个批次全是退化组，被跳过了。

> **一个设计教训**：我第一版把 advantage 传成了 `None`，让 GPU hook 自己去算。
> 这既和我自己的文档矛盾，又把组逻辑推到了「没有卡就测不到」的那一侧。
> 改成在循环里算之后，多出一份纯 Python 实现——于是**自检断言两份实现数值一致**，
> 因为悄悄漂开就意味着循环训练用的 advantage 和损失验证过的不是同一个。

## 19.5 冷启动 SFT：不是可选项

> **大白话**：让一个 1.5B 模型直接上手多跳检索 + 工具调用，它几乎一条都做不对。
> 于是每组 8 条 rollout 全是 0 分，组内标准差 0，advantage 全 0，**梯度精确为零**。
> 你会烧掉几个小时 GPU，reward 曲线一条直线，而 loss 曲线看起来很平静。

所以先做一轮**拒绝采样 SFT**（`rl/train/run_sft.py`）：

1. 用强模型走**同一个 `run_turn`、同一套工具、同一个 preset** 采样。
2. **只保留通过验证器的轨迹**——过滤器就是 GRPO 的奖励函数本身。
3. 按 `(题目, 工具调用名序列)` 去重，每题最多留 2 条。
4. 用**和 GRPO 完全相同的 mask 构造**做交叉熵微调。

两个设计点值得说：

**同一个验证器既当 RL 奖励、又当 SFT 过滤器。** 于是模仿的目标分布
**在构造上**就是奖励函数喜欢的分布，两个阶段不可能在优化不同的东西。

**去重比看起来重要。** 不去重的话，几道容易题会有很多条成功轨迹，
梯度被它们主导，模型学的是那几道题的措辞而不是行为。

**SFT 还是 mask 的金丝雀。** 因为它和 GRPO 共用 `template.pack()` 和
`grpo.masked_cross_entropy`，如果 span 错一个 token、或者停止符在 mask 外，
SFT 要么不收敛、要么产出乱码——**在一次比 RL 便宜得多的运行上、响亮而且早**。

**闸门**：SFT 之后 dev pass@1 没有大致翻倍、格式合法率没上 95%，就停下来查，别碰 GRPO。

## 19.6 在线难度课程

退化组浪费算力，那就别采那些题。但静态过滤**错两次**：

1. **标定错了模型。** 教师 4/8 能解的题，Qwen2.5-1.5B 可能 0/8。
   难度必须对着**待训练的策略**标定。
2. **只标定一次。** 有用的区间会移动——今天 0/8 的题明天会变成 3/8，
   那正是那时最该练的；而今天 4/8 的题明天变成 8/8，就不再教任何东西。
   一次性过滤**扔掉了自己最好的未来数据，留下了最差的**。

所以通过率用运行中**已有的 rollout 持续重估**（`rl/train/curriculum.py`）——
奖励是现成的，它们本来就是为训练算的，重估**免费**。退休也是可逆的。

```python
@property
def active(self) -> bool:
    if self.observations < MIN_OBSERVATIONS:   # 观测太少时假定活跃
        return True
    return ACTIVE_LOW < self.pass_rate < ACTIVE_HIGH
```

`MIN_OBSERVATIONS` 那一行不是保守，是必需：训练最初策略最差，
凭一组 8 条就退休会在前几步把训练集扔掉大半。

## 19.7 权重怎么进 rollout 服务

朴素做法是把 vLLM 跑在同一个进程里，每步优化后把张量拷过去。代价是：
要写权重同步代码，而且单卡上 trainer 的优化器状态和服务的 KV cache 会抢显存。

本项目的做法：**vLLM 独立进程 + LoRA 热插拔**（`rl/train/lora_serve.py`）。
trainer 存下 adapter，服务自己去读。基座权重从不移动，
所以**没有任何东西需要同步**——省掉的正是那一整块代码。

两个容易静默出错的点，都设了守卫：

- **忘了 `VLLM_ALLOW_RUNTIME_LORA_UPDATING=1`** → 端点 404，换权重静默失效（19.4）。
- **换权重必须先卸后装** → 装一个服务已知的名字在某些版本会报错，
  而半完成的交换会留下旧 adapter 继续服务，于是**训练的版本和采样的版本不是同一个**。
  自检直接断言调用顺序是 `unload` → `load`。

adapter 按步号命名（`policy-step-000123`）并盖进轨迹的 `stamp`：
混进离策略数据是很难查的 bug，有了版本号它就变成可核对的。

## 19.8 必须盯的曲线

reward 曲线单独看不出健康与否。`metrics.py` 里这几条各自对应一种它掩盖不住的失败：

| 指标 | 它的失败长什么样 |
|---|---|
| `all_zero_groups` | 完全没有梯度；reward 走平而损失函数里一切正常 |
| `clip_fraction` | ≈0 说明这一步啥也没更新；≈1 说明策略已跑离采样分布 |
| `kl` | 持续上升＝正在漂离参考模型，通常是崩塌前兆 |
| `entropy` | 快速下降＝探索已死，reward 随后必然见顶 |
| `format_valid` | 下降＝策略在丢掉工具协议，不是在变聪明 |
| `gave_up` | 上升＝它学会了「不答比检索更省」 |
| `voided` | 上升＝它找到了刷验证器的办法 |

最后两个对这个环境最要紧，因为 reward hacking 和奖励崩塌就是这样显形的——
而且**它们可以和平均 reward 同时上升**。

参考模型用 `peft` 的 `disable_adapter()` 上下文管理器：LoRA 本来就不动基座权重，
所以**参考策略已经在显存里**，不需要第二份权重。24 GB 卡上这是装得下和装不下的差别。

## 19.9 本章小结

- GRPO 用组内均值当基线，省掉 critic。退化组梯度精确为零但照样花 G 条 rollout，
  `all_zero_groups` 因此是最重要的健康指标，而 reward 曲线看不见它。
- token 级归一化 vs 按序列平均，差别可以算出来：`-0.667 vs +0.000`。
- `logp_old` 必须采样时记录，否则 ratio 恒为 1、裁剪静默失效；
  对位按 prompt 前缀而非顺序，部分覆盖整条丢弃。
- 一步七件事，第七步（换权重）漏掉是最贵的静默故障。
- 冷启动 SFT 不是可选项；它还是 mask 的金丝雀。
- 在线难度课程：对着策略标定、持续重估、可逆退休。
- LoRA 热插拔省掉全部权重同步代码，代价是两个必须设守卫的坑。
