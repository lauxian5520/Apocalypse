# 04 · Harness 总览与两大设计原则

> 从这一章开始是全教程的核心。建议对照实际代码 `backend/harness/` 目录一起看。

## 4.1 Harness 是什么

**Harness（智能体工作台）**是部署在天启网站上的一个独立子系统，访问路径 `/harness.html`。
它参照了 `deepseek-ai/deepseek-harness` 的两个核心设计思想重新实现（不是照搬其 TypeScript 代码），
本质上是一个**最小可用的 Agent Runtime**：给一个 LLM 配上工具调用能力、人工审批、沙箱执行环境、
完整的可追溯日志、上下文压缩、多智能体委派。

> **严谨定义**：Agent Runtime（智能体运行时）指一套支撑"LLM 反复思考-调用工具-观察结果-再思考"
> 这一循环（通常称为 ReAct 循环：Reasoning + Acting）稳定运行的工程基础设施，包括但不限于：
> 消息拼装、工具调用解析与执行、权限控制、状态持久化、错误恢复。
>
> **大白话**：ChatGPT 网页版你看到的是"一问一答"，但背后如果这个模型能自己调用工具（搜索、写代码、
> 跑命令），就需要一整套"脚手架"去处理："模型说要调用哪个工具？参数对不对？敢不敢真的执行？
> 执行结果怎么喂回给模型？模型会不会陷入死循环？中途网页关了怎么办？"——这套脚手架就是 Harness，
> 跟 Claude Code、Cursor Agent、Devin 背后的核心机制是同一类东西。

## 4.2 为什么这部分对求职最有价值

LLM Post-Train / Agent 开发岗位的面试，最怕的就是候选人只会说"我用 LangChain 搭了一个 Agent"——
这句话信息量几乎为零，因为 LangChain 把所有工程细节都封装掉了，面试官问不出你真正理解了什么。
而这个项目是**从裸的 HTTP 请求开始，自己实现了整套 Agent Runtime**，这意味着你能回答面试官任何一个
"往下再问一层"的问题：

- "工具调用的流式响应怎么解析？"——能讲清楚 `_ToolCallAccumulator` 怎么按 `index` 拼接分片参数。
- "如果用户中途关掉浏览器，Agent 还在执行怎么办？"——能讲清楚 `BackgroundTask` + `reconcile_status`
  的兜底机制。
- "上下文超长了怎么办？"——能讲清楚基于真实 `prompt_tokens` 而非本地估算的压缩触发条件。
- "多个 Agent 互相调用会不会失控？"——能讲清楚四道花钱闸门和"子代理内部审批直接拒绝"的设计。

这些都是本教程后续章节要讲的内容。

## 4.3 设计原则一：可替换的能力接缝（Replaceable Seams）

> **严谨定义**：接缝（Seam）在软件设计中指系统里"可以在不修改调用方代码的前提下，独立替换其行为"
> 的一个点，通常通过面向接口编程（这里是 Python 的 `Protocol`，即结构化类型协议）实现。
>
> **大白话**：给关键组件都套一层"插座"——用电器的时候你不用管电到底是水电还是火电发的，只要插头
> 规格（协议）对得上就能用。Harness 里有四个这样的"插座"：

| 接缝 | 协议定义在 | 默认实现 | 换成什么样才需要改代码 |
|---|---|---|---|
| `SessionStore` | `session/store.py` | `SqliteSessionStore` | 换成 Redis/Postgres 存储事件日志 |
| `ModelAdapter` | `llm/base.py` | `OpenAICompatibleAdapter` | 接入不兼容 OpenAI 协议的模型 |
| `Sandbox` | `sandbox/base.py` | `LocalSandbox` | 换成真正的容器级隔离（如 gVisor/Firecracker） |
| `ToolRegistry` | `tools/registry.py` | 基于契约文件扫描 | 换成远程工具注册中心 |

这四个接缝全部在 `harness/context.py::build_context()` 一处被"组装"起来——这是整个系统**唯一**
挑选具体实现的地方，其余所有代码只依赖协议类型（类型注解写的是 `Any`/Protocol，不是具体类）。

```python
# 大致形状（详见 05 章）
def build_context(session_id, preset) -> HarnessContext:
    return HarnessContext(
        store=SqliteSessionStore(),
        llm=build_adapter(model),
        tools=ToolRegistry(preset),
        sandbox=LocalSandbox(workspace),
        hooks=build_hooks(),
        ...
    )
```

**这为什么重要**：这是"依赖倒置原则（Dependency Inversion）"的教科书级实践——高层模块（Agent 循环）
不依赖低层模块（具体的 SQLite 实现）的细节，两者都依赖抽象（Protocol）。面试被问"如果要把存储换成
PostgreSQL 你会怎么改"，答案应该是"只改 `build_context` 这一行，新写一个实现 `SessionStore` 协议的
类"——这说明你理解这个设计的意图，而不是背答案。

## 4.4 设计原则二：全链路可追溯（Everything the Model Sees Is Logged First）

这是比第一条更核心、更"反直觉"的设计约束：

> **不变量**：发给模型的每一条消息，必须先作为一个事件写进 append-only（只追加）的会话日志，
> 然后才能被用来构造下一次请求。`harness/session/projection.py::derive_messages()` 是**唯一**
> 被允许把日志转换成模型请求消息的函数。

> **严谨定义**：Append-Only Log（只追加日志）指一种只允许在末尾添加新记录、不允许修改或删除已有
> 记录的数据结构；配合"当前状态由日志重放推导得出"，就是前面提过的事件溯源（Event Sourcing）模式。
>
> **大白话**：这条规则听起来像是"多此一举"——为什么不直接维护一个 `messages = [...]` 列表，
> 模型说什么就往里 append，要发请求时直接拿去用？因为这样做会导致一个致命问题：**"模型实际看到的
> 东西"和"你以为模型看到的东西"可能会悄悄分叉**。举个例子——如果系统提示词里嵌入了当天日期，
> 你在"读取历史会话、重新渲染"的时候如果重新计算一遍系统提示词，得到的日期就变成了"今天"，
> 而不是模型当时真正看到的那个日期。日志里没记下来的东西，永远无法准确复原。

这个不变量在代码里具体怎么落地，`harness/loop/agent.py` 里的循环**先执行 `emit()`（写日志），
再把这个事件 yield 给上层（用于 SSE 推送给前端）**——顺序不能反，如果反过来，前端可能会看到一个
"还没真正持久化"的事件，一旦这时候进程崩溃，前端展示过的东西和日志里实际存在的东西就对不上了。

### 系统提示词快照就是这条规则的直接后果

系统提示词本身会随 `config/change` 事件写进日志（仅在内容变化时才写一次，不是每条消息都重复记）。
为什么连"系统提示词"这种看起来是"配置"而不是"对话内容"的东西也要进日志？正是因为它：

1. 嵌入了当天日期；
2. 由 `system.md` 文件拼出来，这个文件本身也会被改动。

如果历史会话被重放时"实时重新计算"系统提示词，会出现两个问题：显示的日期变成了重放那天而不是
对话发生那天；如果 `system.md` 后来被改过，所有历史会话的"系统提示词"会被整体篡改，而模型当时
根本没看过这个新版本。所以 `derive_messages()` 的规则是：**优先用日志里记录的快照，只有旧版本
（早于快照机制上线前）留下的会话，才回退用当前配置现算**。

## 4.5 一次完整对话（Turn）里发生了什么——先看全貌

```
turn/start
  step/start → assistant/chunk… → assistant/message → llm/usage
            → tool/call → [审批] → tool/result
  step/end  → （还有工具要调就再来一步）
turn/end
```

- **Turn（轮次）**：用户发一条消息，到模型给出最终不再调用工具的回复为止的完整交互。
- **Step（步）**：一个 Turn 内部，"模型说一句话（可能带工具调用）→ 执行工具 → 把结果喂回去"算一步。
  一个 Turn 可能包含多个 Step（模型连续调用好几轮工具才给出最终答案）。

事件类型采用和上游项目一致的"斜杠命名法"（如 `tool/call`、`step/end`）。其中**只有**
`user/message`、`assistant/message`、`tool/result` 三种事件会被投影成真正发给模型的消息，
其余（`assistant/chunk` 流式分片、各种 `step/*`/`llm/usage` 元事件）**只用于日志、重放、
前端轨迹视图**，不会占用模型的上下文窗口。

这张图和这条"只有三种事件会投影"的规则，会在 [05](05-harness-事件系统与会话存储.md) 和
[06](06-harness-Agent执行循环.md) 里被逐字拆开讲清楚每一步具体在代码里怎么实现的。

## 4.6 本章小结 —— 面试一句话总结怎么说

> "这个 Harness 子系统有两个贯穿全局的设计约束：第一，模型适配器、工具注册表、会话存储、沙箱
> 这四个关键组件都是'一个协议加一个默认实现'，全部在一个装配点里选定，方便替换；第二，模型看到的
> 每一条消息必须先写进一个只能追加的事件日志，再由唯一一个投影函数转换成请求，这样可以保证'历史
> 展示的内容'和'当时模型真实看到的内容'永远一致，即使系统提示词本身会随日期变化。"

这两句话说完，几乎必然会引出面试官的追问——下面几章就是这些追问的答案。
