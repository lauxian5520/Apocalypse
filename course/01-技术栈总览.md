# 01 · 技术栈总览

## 1.1 项目定位

天启是一个**单体应用（Monolith）**：一个 FastAPI 后端进程，既提供 REST/SSE API，也直接托管前端静态文件。
默认数据库是 SQLite，也可以切到 MySQL / PostgreSQL。没有前端构建工具（不用 Webpack/Vite），
前端是纯 HTML + 原生 JS + CSS，浏览器直接加载运行。

> **严谨定义**：单体应用（Monolith）指所有功能模块打包进同一个可部署单元、共享同一个进程和数据库连接池的
> 架构风格，与"微服务（每个功能拆成独立服务、独立部署）"相对。
>
> **大白话**：不是所有项目都需要拆成十几个 Docker 容器互相用 gRPC 聊天。对于一个人维护的个人网站，
> "一个进程搞定一切"更简单、更好调试、部署成本更低。技术选型要匹配项目规模，不是越复杂越高级。

## 1.2 后端技术栈

| 技术 | 版本约束 | 用途 | 面试可以怎么说 |
|---|---|---|---|
| **FastAPI** | ≥0.115 | Web 框架，基于 Starlette + Pydantic | 用了依赖注入（`Depends`）做认证、异步原生支持 SSE 流式响应 |
| **Uvicorn** | ≥0.34 | ASGI 服务器 | 生产环境跑在 Docker 里，前面挂 nginx 反代 |
| **SQLAlchemy** | ≥2.0 | ORM | 用的是 2.0 风格（`DeclarativeBase`），不是旧的 `declarative_base()` |
| **Pydantic / pydantic-settings** | ≥2.3 | 数据校验 + 配置管理 | `Settings(BaseSettings)` 从 `.env` 读配置，`@model_validator` 做路径解析 |
| **python-jose** | ≥3.3 | JWT 编解码 | HS256 签名，`HttpOnly` Cookie 承载 |
| **passlib + bcrypt** | 固定 `bcrypt==4.0.1` | 密码哈希 | **注意这里有个真实的版本坑**（见下文） |
| **httpx** | ≥0.27 | 异步 HTTP 客户端 | **手写**调用 LLM 的 `/chat/completions` 接口，没有用官方 `openai` SDK |
| **sse-starlette** | ≥2.1 | （声明了但项目自己手写了 SSE 帧格式，未实际使用其封装） | 体现"依赖没删干净"是真实项目的常态 |
| **apscheduler** | ≥3.10 | 定时任务 | 定时抓取 GitHub Trending / HuggingFace 论文等 |
| **BeautifulSoup4** | ≥4.12 | HTML 解析 | 爬虫模块、`web_fetch`/`web_search` 工具用它清洗网页正文 |
| **python-docx / python-pptx / pypandoc** | 固定版本 | Harness 的 docx/pptx 技能 | 生成 Word/PPT，`pypandoc_binary` 内置 pandoc 二进制，不需要额外装系统包 |
| **alembic / zai-sdk** | — | 声明在 `requirements.txt` 但未实际使用 | 见下文"未使用依赖"说明 |

### 一个真实的版本坑：bcrypt 固定版本

`requirements.txt` 里 `bcrypt==4.0.1` 被死死钉住，还专门写了注释解释原因：`passlib==1.7.4`
在初始化时会读取 `bcrypt.__about__.__version__`，而 `bcrypt>=4.1` 移除了这个属性；同时新版
`bcrypt` 遇到超过 72 字节的密码会直接抛异常，而不是像旧版本那样自动截断。这是**依赖库之间"版本组合"
导致的真实故障**，面试时如果被问"你在项目里遇到过什么坑"，这是一个很好的、具体的、可验证的例子——
比空泛地说"踩过很多坑"有说服力得多。

### 未使用依赖也是信息

`alembic`（数据库迁移工具）和 `zai-sdk`（智谱官方 SDK）在依赖清单里，但项目里没有真正用它们——
数据库变更用的是 `models/migrations.py` 里手写的轻量补丁逻辑（见 [02](02-后端分层架构.md)），
调智谱 API 走的是和其他 provider 一样的手写 `httpx` 请求。这提示你：**真实项目的依赖列表会有历史遗留**，
review 代码时要分清"声明了"和"真的在用"，这也是一种工程素养。

## 1.3 前端技术栈

**没有框架**——不用 React/Vue/Angular，不用打包工具。原因很朴素：这是一个页面跳转式的多页应用
（每个 `.html` 是独立入口），交互复杂度没有高到需要虚拟 DOM 和组件化状态管理的程度。

| 技术 | 用途 |
|---|---|
| 原生 HTML/CSS/JS | 无内联脚本/样式，`<script src>` 按固定顺序加载 |
| `fetch` API | 所有网络请求，封装出 `apiFetch()`（自动带 CSRF）和流式场景下的裸 `fetch` |
| SSE（Server-Sent Events） | 用于 AI 精灵聊天和 Harness 流式对话，不是 WebSocket |
| CSS 变量 + 分层组织 | `base.css`（设计变量）+ `components/`（可复用部件）+ `pages/`（页面专属） |
| Three.js（按需） | 3D 精灵渲染，加载失败时有降级方案（见 [03](03-前端架构.md)） |

## 1.4 数据存储

- **SQLite**（默认）：单文件数据库，`var/db/myweb.db`。适合个人项目，零运维成本。
- 通过 `DB_TYPE` 环境变量可切换到 **MySQL / PostgreSQL**（`pymysql` / `psycopg2-binary` 已在依赖里备好）。
- 运行时所有可变数据（数据库文件、上传文件、音乐、抓取缓存、Agent 工作区）统一放在 `var/` 目录下，
  这是"单卷备份"设计——Docker 部署时只需要挂载一个 `./var` 卷。

> **面试话术**：这个项目体现了"配置驱动而非代码驱动"的可移植性设计——数据库类型、AI 供应商、
> Harness 是否开启 shell 权限，全部是环境变量，不需要改代码、不需要重新构建镜像就能切换部署形态。

## 1.5 部署技术栈

- **Docker + docker-compose**：两个服务，`backend`（FastAPI 应用）+ `nginx`（反向代理 + 静态文件托管）。
- **nginx** 负责：托管前端静态文件、反代 `/api/` 到后端、**关闭代理层缓冲**（`proxy_buffering off`）
  以保证 SSE 流式响应不被 nginx 攒批延迟。
- 容器安全加固：`cap_drop: [ALL]`、`no-new-privileges`、`pids_limit`、非 root 用户（uid 10001）运行——
  这是因为 Harness 会让 Agent 在容器内执行 shell 命令，容器本身的权限面必须收到最小。

## 1.6 为什么这套技术栈值得在面试中细讲

这个项目不是"调一个 API 拼一个 Demo"，而是从底层自己实现了：

1. **事件溯源的会话存储**（不是简单地存一个 messages 数组）；
2. **手写的、面向 Function Calling 的流式 LLM 客户端**（没有依赖 `openai` SDK，自己解析 SSE、自己
   拼接分片的 tool_call 参数）；
3. **进程内的 execve 沙箱**（不是 Docker-in-Docker，而是用 `setrlimit` + `execve` 直接在宿主进程里做
   资源与路径隔离）；
4. **数据与代码分离**的插件式工具/技能/子代理系统。

这些都是 Agent Infra 岗位面试官真正想看到的东西——不是"你会不会调 API"，而是"你是否理解 Agent
系统内部的工程权衡"。后续章节，尤其是 04～11，会把这些逐一拆开讲透。
