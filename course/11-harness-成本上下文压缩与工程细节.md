# 11 · 成本、上下文压缩与一批"血泪教训"级工程细节

这一章汇总一批分散但极其重要的实现细节——它们大多是"没有踩过坑就写不出来"的代码，
是面试时最能体现你"真读过、真理解"这个项目，而不是"背了一份 README" 的地方。

## 11.1 模型适配器：`llm/base.py` 与 `openai_compatible.py`

### 一个类型设计上的小巧思：`LLMDelta`

```python
@dataclass
class LLMDelta:
    content: str | None
    reasoning: str | None
    result: LLMResult | None    # 只有流式的"最后一条"才不是 None
```

流式接口的生成器（`stream()`）每次 `yield` 出来的都是同一种类型 `LLMDelta`——中间的分片
和最后汇总完的最终结果，**用同一个类型表达，靠 `result is not None` 来区分"这是不是最后一条"**。

> **大白话**：这是一个"用类型系统防呆"的例子——如果流式分片和最终结果是两种不同的类型
> （比如分片是字符串、最终结果是另一个专门的对象），调用方很容易写出"忘记处理最终结果，
> 只顾着攒分片"的 bug（因为分片处理起来更"顺手"，最终结果的处理逻辑容易被落下）。
> 现在两者是同一种类型，调用方必然要在循环体里判断 `delta.result is not None`，
> 结构上就不太可能"漏掉"收集最终结果这一步。

### `stream()` 里怎么把分片拼成完整的 tool_call

OpenAI 兼容协议里，流式返回的 tool_call 参数是**分片**发的（一个字一个字地吐出 JSON
字符串片段），provider 保证每个分片都带一个稳定的 `index`（这是唯一保证每次都在的字段），
但 `function.name` 往往**只在这个调用的第一个分片里出现一次**。适配器内部用一个
`_ToolCallAccumulator`，以 `index` 为 key，把同一个 `index` 下所有分片的 `arguments`
字符串拼接起来，如果 provider 没给 `id`，就自己生成一个 `call_{n}` 的兜底 id；
如果收完所有分片后名字始终是空的，就丢弃这个调用（认为它是一次无效的分片流）。

> **面试话术**：这是解析 OpenAI 风格流式 Function Calling 响应时**几乎每个自己写过
> 适配层的人都会踩到**的坑——很多人第一次写会假设"每个分片都带全部字段"，直到遇到
> 真实的流式响应才发现 name 只在第一片出现。能讲清楚这一点，比"我用官方 SDK，
> 它帮我处理好了"更能体现底层理解。

### 报错要读实际的错误体，不能信任框架的默认异常

```python
async def _raise_for_stream_status(response):
    if response.status_code >= 400:
        body = await response.aread()   # 手动读一遍原始响应体
        raise UpstreamError(f"...：{body[:500]}")
```

流式响应里如果直接调用 httpx 的 `response.raise_for_status()`，抛出的异常信息通常
**不包含 provider 返回的具体错误描述**（因为响应体是流式的，还没被读取），报错信息
往往只有一个笼统的"400 Bad Request"，看不出到底是哪个字段传错了。手动先把响应体读出来
再抛异常，报错信息里能带上 provider 真正返回的具体原因（比如"某个参数超出取值范围"）——
这类"多一步手动处理，换来更有用的报错信息"的细节，往往是区分"随手对接一下 API"和
"认真调试过真实故障"的分水岭。

### 思考型模型的"空回复"陷阱

CLAUDE.md 原文强调的一个真实故障：

> "`deepseek-v4-pro` 这类思考型模型，会先花掉输出预算做推理，再吐出正文。所以标题、摘要
> 这类短输出场景的 `max_tokens` 必须留足余量；预算给小了会拿到空正文，此时适配器直接
> 报错而不是返回空串——这个坑最初就是靠这条报错才发现的。"

> **严谨定义**：一些"推理增强型（Reasoning）"模型在正式生成回复内容之前，会先生成一段
> 不直接展示给用户、但同样占用输出 token 预算的"思维链（Chain of Thought）"内容。
> 如果给这类模型设置的 `max_tokens` 太小，模型可能把整个预算都花在了思考过程上，
> 还没来得及生成真正的正文就被截断了——`finish_reason` 会是 `"length"`，但 `content`
> 字段却是空字符串。
>
> **大白话**：你以为设置了 `max_tokens=100` 是"回复最多 100 个 token"，但对思考型模型
> 来说这个预算可能全部被"脑内 OS"占用了，正文一个字都没写出来。**如果代码把这种情况
> 静静地当成"模型回复了一个空字符串"处理**，表现出来的症状是"标题生成器偶尔生成一个
> 空标题""摘要功能偶尔返回空白"——这种 bug 极难排查，因为程序没有报错、逻辑看起来
> 全部走通了，只是结果碰巧是空的。真正的修复方式是——**遇到 `finish_reason == "length"`
> 且 content 为空，直接抛出一个明确的异常**，而不是把这种异常状态悄悄降级成一个"正常但
> 空洞"的返回值。这是"绝不用一个合法但错误的默认值去掩盖异常状态"这条工程原则
> （很多语言里"空字符串/None/0"这类默认值，特别容易被无意间用来悄悄吞掉本该报出来的错误）
> 的具体案例。

这也解释了为什么标题生成（`title.py` 的 `TITLE_MAX_TOKENS=512`）和压缩摘要
（`compaction.py` 的 `SUMMARY_MAX_TOKENS=3000`）的 `max_tokens` 设得看起来"过于宽裕"——
表面上只是要"一个十几个字的标题"或者"几百字的摘要"，但要给思考型模型留出足够的"思考预算"，
否则就会撞上上面这个坑。

## 11.2 上下文压缩：真实 token 数，而不是本地估算

[05](05-harness-事件系统与会话存储.md) 讲过 `estimate_tokens()` 是一个粗糙的字符数估算，
这里补充压缩**真正**的触发判断——`compaction.py::_measured_prompt_tokens()`：

```python
def _measured_prompt_tokens(log):
    usage_event = latest(log, type=LLM_USAGE)
    compaction_event = latest(log, type=COMPACTION_SUMMARY)
    if compaction_event and usage_event.seq <= compaction_event.seq:
        return None   # 这次测量描述的是压缩之前的上下文，已经不能代表现在
    return usage_event.data["prompt_tokens"]
```

只有在"最近一次真实用量数据，比最近一次压缩摘要还新"的前提下，才信任这份测量值；否则
说明这份用量数据描述的是"压缩之前那个已经不存在的上下文",要退回用 `estimate_tokens()`
现算。

### 为什么要用 provider 返回的真实值，而不是自己估算

代码注释里给出了一个真实观测的数字对比：某次测量里，真实 `prompt_tokens` 是 **9,874**，
而本地估算只有 **426**——差了二十多倍。原因是**每次请求除了对话本身，还要带上完整的
系统提示词和全部工具的 JSON Schema**，这些固定开销加起来通常有 1500～2000+ token，
而 `estimate_tokens()` 只统计了"对话文本"这一部分，完全没算上这两项。

> **大白话**：如果压缩触发条件用的是这个严重偏低的估算值，会导致"用户设置的上下文预算
> 明明已经快被真实占满了，系统却还傻乎乎地以为'才用了 426 个 token，远没到阈值，不用压缩'"——
> 结果就是下一次请求直接因为超出模型的上下文窗口而报错，而不是提前触发压缩。**决策依据
> 必须尽可能贴近真实情况**，本地估算只配拿来做"某个数字大概长什么样"的粗略判断，
> 真正关键的、影响系统行为的决策，要用权威数据源（这里是 provider 明确返回的计费用量）。

### 拒绝"无效压缩"：`MIN_COMPACTION_GAIN_TOKENS`

```python
gain = _compactable_tokens(log, before_boundary) - _compactable_tokens(log, after_boundary)
if gain < 500:
    logger.warning("压缩收益过小，请提高 HARNESS_CONTEXT_BUDGET_TOKENS")
    return log   # 直接返回原始日志，不做任何压缩
```

> **大白话**：假设一次请求的固定开销就有 1800 个 token（系统提示词+工具 schema），
> 而用户设置的预算只有 2000 token——那压缩再狠，用完的 token 数也压不下多少，很可能
> 每一步都要重新触发一次压缩、每次都要花一次 LLM 调用去做摘要，陷入"越压缩越花钱、
> 却几乎没有效果"的死循环。这里设了一个"最低收益门槛"（500 token）——如果预计压缩下来
> 省不了这么多，宁可拒绝压缩、打一条明确的、可操作的警告日志（告诉部署方该调高预算
> 配置了），也不要每一步都白白多花一次摘要请求的钱去做一件几乎没用的事。这是"及早暴露
> 配置问题，而不是让系统用一种低效但'看起来在工作'的方式默默硬扛"的工程直觉。

## 11.3 系统提示词只带日期：为了前缀缓存

```
系统提示词最后一段（易变部分）：今天是 2026-09-10。
```

**故意不写精确到秒的时间戳**——原因和 [07](07-harness-工具系统与审批.md) 讲的工具顺序
排序是同一个道理：只要系统提示词这一整段内容**逐字节完全一样**，provider 的前缀缓存
才能命中；带上秒级时间戳，意味着**每一次请求的系统提示词都不一样**，前缀缓存永远失效。
README 给出了实测的具体收益数字：这项优化能省下大约 **8000～9900** 个输入 token
（针对一次典型请求）。

需要精确到秒/分的时刻，改由 `current_time` 工具在被调用的那一刻本地读取——它不联网，
读的是**运行这个后端服务的服务器自己的系统时钟和时区**。这里还有一个真实的部署注意事项：
Docker 容器默认时区是 UTC，如果部署方希望 Agent 感知到的是本地时间，需要在
`docker-compose.yml` 里给 backend 服务额外加一条 `environment: TZ: Asia/Shanghai`
（或对应的时区）——这是一个"文档里明确写出来提醒部署方，否则会在生产环境里悄悄踩坑"
的细节。

## 11.4 计费：未知的价格显示"—"，而不是 0

```python
def estimate_cost(model, usage):
    price = pricing_table.get(model)
    if price is None:
        return None      # 而不是 0.0
```

`data/pricing.json` 是一份纯数据文件，表里查不到的模型，`estimate_cost` 返回 `None`，
前端渲染成"—"（一个明确表示"未知"的占位符），**不是** 0——如果返回 0，用户看到的信息
是"这次调用免费"，这是一个彻头彻尾的谬误，可能误导用户对成本的判断。而且这个"未知"
具有"传染性"：`pricing.summarize()` 汇总一整个会话（包括所有子代理）的总费用时，
**只要有任何一次调用的模型价格未知，整个会话的总费用就是 `None`，不会是一个"看起来精确
但其实是错误低估"的部分总和**。

> **面试话术**：这是"缺失数据不该被静默替换成一个'看起来合理但实际错误'的默认值"这条
> 原则，在计费场景下的又一次具体应用——和 11.1 节里"思考型模型空回复要报错，不能返回
> 空字符串"是同一种设计哲学的两处不同体现。这种"同一个原则在不同模块里反复出现"的一致性，
> 正是判断一个系统"是不是真的有设计思路"，还是"东一榔头西一棒子的补丁堆砌"的一个信号。

价格本身会变，`data/pricing.json` 是数据文件，README 明确提醒需要对照官方定价页面自行
核对——**token 数无论价格准不准，都是准确的**，因为它直接来自 provider 的 API 响应，
不依赖这份本地维护的价格表。

## 11.5 自动生成标题

```python
def generate_title(llm, first_message):
    try:
        title = llm.complete(prompt_from("data/prompts/title.md", first_message),
                              max_tokens=512)
        title = strip_quotes_brackets_periods(title)[:40]
        return title
    except Exception:
        logger.info(...)
        return ""    # 静默失败，因为这只是一个装饰性功能
```

对比压缩摘要（失败会用警告日志提醒、影响后续对话质量）和标题生成——标题**纯粹是装饰性**
的（不影响对话本身能否进行），所以这里的失败处理策略明显更"宽松"：捕获所有异常，
只记一条 `info` 级别日志，返回空字符串，不打扰用户。这是"根据一个功能对核心业务的重要性
程度，决定它的失败该多大声地被感知到"的又一处体现——同样是"失败了怎么办"，压缩摘要选择
"打警告日志"，标题生成选择"静默降级"，都是刻意权衡后的结果，不是随手写的。

## 11.6 本章小结：这些细节共同讲的是同一件事

回顾这一章的六个小节，会发现它们其实都在反复论证同一条工程原则的不同侧面：

> **"不要用一个'看起来正常'的默认值去掩盖一个真正需要被感知到的异常状态；
> 决策所依赖的数据，要尽可能是权威的、真实的，而不是图省事的估算。"**

- 空正文该报错，不该悄悄返回空字符串；
- 未知价格该显示"—"，不该显示 0；
- 压缩触发该用 provider 真实返回的 token 数，不该只信本地粗估算；
- 收益太小的压缩该拒绝执行并明确警告，不该假装执行了一次"象征性"的压缩。

这条主线贯穿全书，也是面试时如果被问"这个项目里你觉得最值得称道的设计是什么"，
一个非常扎实的回答方向——不是某一个具体功能，而是这条反复被应用的一致性原则。

事件流渲染成一个可交互的界面。
