# 第一部分 · LLM 基础知识速成

## 1.1 大模型是怎么"说话"的：自回归生成与 Token

> **严谨定义**：当前主流的大语言模型（LLM）本质上是一个**自回归（Autoregressive）**语言模型——
> 给定前面已经出现的一串 token，模型输出"下一个 token 是什么"的概率分布，采样出一个 token
> 拼到序列末尾，再重复这个过程，直到生成一个表示"结束"的特殊 token 或达到长度上限。
>
> **大白话**：模型不是"一次性想好整句话再说出来"，而是像你手机输入法的联想候选，
> 但是**逐字**地不断"猜下一个字最可能是什么"，猜一个吐一个，吐出来的字又变成下一次猜测的
> 输入。ChatGPT 网页版那种"一个字一个字蹦出来"的效果，就是这个过程被实时展示出来的样子——
> 不是打字机特效，是它真的在一个字一个字地算。

**Token 不等于"字"**：中文大致 1 个字≈1 个 token，英文常见词也是 1 个 token，
但长的英文单词会被拆成好几个 token（比如 "internationalization" 可能拆成
"international" + "ization"）。这也是为什么本项目 `harness/session/projection.py::estimate_tokens()`
用"总字符数 / 2.5"来粗估 token 数——中英文混合场景下这是一个经验折中值（详见第二部分）。

## 1.2 上下文窗口：模型的"短期记忆"

> **严谨定义**：上下文窗口（Context Window）指模型单次推理能接收的最大 token 数——
> 包括你发送的所有输入（系统提示词、历史对话、工具定义）加上模型将要生成的输出，
> 总和不能超过这个上限。
>
> **大白话**：模型没有"记住之前聊过什么"的能力，它每次回答问题，都是把**从头到现在的
> 全部对话文本**当作一次全新的输入重新读一遍。所以"上下文窗口"越大，模型能"记住"的历史
> 就越长；但窗口是有限的，聊得越久，这些文本占的空间就越大，直到有一天必须"扔掉"或
> "压缩"一部分早期内容——这正是本项目"上下文压缩"功能存在的原因（第二部分 2.10 节）。

多轮对话为什么能"记住"上文？**不是模型有记忆**，而是每次请求都把完整的历史消息列表
（`[{"role": "system", ...}, {"role": "user", ...}, {"role": "assistant", ...}, ...]`）
重新发一遍给模型。这也是这个项目"事件溯源式会话存储"存在的直接原因——既然每次都要
重新拼出这份历史，就必须有一个可靠的地方能把它准确地拼出来。

## 1.3 三种角色：System / User / Assistant

OpenAI 定义的 Chat Completions 协议里，每条消息都带一个 `role` 字段：

| 角色 | 作用 |
|---|---|
| `system` | 定义模型的"人设"和行为规则，通常放在消息列表最前面，一次对话通常只有一条（或没有） |
| `user` | 用户说的话 |
| `assistant` | 模型自己说的话（包括之前几轮的回复） |
| `tool` | 工具调用的执行结果（也叫 `function`，取决于协议版本），喂回给模型 |

> **大白话**：把这想象成一部剧本——`system` 是"人物小传"（这个角色是谁、说话风格是什么），
> `user`/`assistant` 是对话台词，`tool` 是"旁白：他打开了那份文件，看到了……"。模型每次
> "发言"，都是先把整个剧本从头读一遍，再决定自己这句台词该说什么。

本项目里，"天启精灵"的人设写在 `backend/data/prompts/sprite.md`，Harness 的系统提示词
由 `system.md` + 运行时信息（日期、工具目录）拼成——都对应这里的 `system` 角色。

## 1.4 采样参数：温度、Top-p，以及为什么"确定性"任务要调低它们

模型在每一步"猜下一个 token"时，并不是永远选"概率最高的那个"，而是按概率分布**采样**。
两个常见的调节旋钮：

> **严谨定义**：**温度（Temperature）**是对概率分布做的一次缩放——温度越低，概率分布越
> "尖锐"（高概率的 token 更容易被选中，模型更"确定"）；温度越高，分布越"平坦"（低概率的
> token 也有更大机会被选中，输出更"有创意"、也更容易"胡说"）。**Top-p（Nucleus Sampling）**
> 只在"累积概率达到 p 的最小 token 集合"里采样，把极小概率的候选直接排除掉。
>
> **大白话**：温度调低=让模型"少来点花样，按最靠谱的说"；温度调高=让模型"天马行空一点"。
> 写诗、头脑风暴适合调高，写代码、回答事实性问题、Function Calling 这种"格式必须精确"的
> 场景，温度通常要调低甚至设成 0。

这也是为什么 `rl/env/adapter.py` 里训练/评估用的 `EvalAdapter`/`PolicyAdapter` 要**自己
控制温度**，而不能复用聊天场景那套默认参数——RL 训练需要在"探索（温度高一点，见到更多样的
轨迹）"和"复现性（同样的 prompt 应该得到可预期的分布）"之间做取舍，这和网页聊天场景的
默认设置目标完全不同。

## 1.5 Function Calling（工具调用）：模型怎么"使唤"外部世界

这是整个 Harness 子系统的根基，也是最容易被误解的一个概念。

> **严谨定义**：Function Calling 指 LLM 服务在请求里额外接收一份"函数目录"（每个函数的
> 名字、描述、参数的 JSON Schema），模型在生成回复时，可以选择输出一个结构化的"我要调用
> 某个函数、参数是这些"的请求，而不是直接输出自然语言。**模型本身不会真正执行这个函数**——
> 它只是"请求"，真正的执行、以及把执行结果重新喂回给模型，都是调用方（你的服务端代码）
> 的责任。
>
> **大白话**：很多人第一次听到"模型能调用工具"，会以为模型内部真的跑了一段代码。
> 实际上模型做的事情，更像是**填一张申请表**："我想用'查天气'这个功能，参数是'北京'"，
> 然后把这张表交给你。你（服务端）拿着这张表，真的去调一次天气 API，把结果拿回来，
> 写成一条新的消息（`role: "tool"`）追加进对话历史，**再把整个对话重新发给模型一次**，
> 模型才能"看到"刚才那次调用的结果，继续往下说。**一次工具调用，背后是两次完整的 HTTP
> 请求**，不是一次。

一次带工具调用的对话轮，在协议层面长这样（简化版）：

```
请求 1：
  messages: [system, user: "北京今天天气怎么样"]
  tools: [{ name: "get_weather", parameters: {city: string} }]
→ 响应 1：
  assistant 消息，content 可能为空，tool_calls: [{id: "call_1", name: "get_weather", arguments: '{"city":"北京"}'}]

（服务端真正执行 get_weather("北京")，得到 "晴，15℃"）

请求 2：
  messages: [system, user: "北京今天天气怎么样", assistant(带tool_calls), tool(call_1结果: "晴，15℃")]
→ 响应 2：
  assistant 消息，content: "北京今天晴，气温 15℃。"
```

这正是本项目 `harness/loop/agent.py::_drive()` 那个循环在做的事——**每一步都是"发一次
请求 → 看模型要不要调工具 → 调完再发一次请求"**，直到模型某一步的响应不再带 `tool_calls`
为止（见第二部分 2.7 节）。"Agent"这个词，工程上很大程度上就是"这个循环 + 一组可调用的
工具"。

**流式场景下工具调用是分片返回的**——这是几乎每个自己写过适配层的人都会踩的坑，
本项目 `harness/llm/openai_compatible.py` 里专门有一个 `_ToolCallAccumulator` 来处理
（详见第二部分 2.11 节）。

## 1.6 流式输出与 SSE

> **严谨定义**：Server-Sent Events（SSE）是一种基于 HTTP 长连接、服务端可以持续向客户端
> 推送文本事件的协议——本质是一个一直不关闭的 HTTP 响应，服务端每准备好一点数据就往这个
> 连接里写一段，格式是 `data: <内容>\n\n`。相比 WebSocket，SSE 是单向的（只能服务端推
> 客户端）、天然基于 HTTP（不需要单独的协议升级），浏览器原生支持自动重连。
>
> **大白话**：如果不用流式，你发一个问题给模型，要等模型**把整句话全部生成完**才能看到
> 任何文字——对一段几百字的回复，这可能要等好几秒，体验很差。流式输出让服务端"模型每吐
> 出一个字，就立刻转发一个字给你"，你看到的就是逐字蹦出来的效果，虽然总耗时没变，但"第一个
> 字出现的时间"大大缩短了，体验好很多。

本项目 SSE 帧的格式在 `backend/core/sse.py`：`f"data: {json.dumps(payload)}\n\n"`——
注意 `data:` 后面那个空格，前端用 `line.slice(6)` 精确按 6 个字符切片，这是一个"看起来可以
优化、实际上有跨文件契约"的典型例子（详见第二部分 2.2 节）。

## 1.7 RAG 与检索：为什么模型"看过互联网"还是会答错

> **严谨定义**：检索增强生成（Retrieval-Augmented Generation，RAG）指在模型生成回答之前，
> 先从一个外部知识库里**检索**出和问题相关的文档片段，把这些片段作为上下文一起交给模型，
> 让模型"参考资料作答"，而不是完全依赖训练时记住的知识。
>
> **大白话**：模型的知识来自训练数据，训练数据有截止日期，也不可能覆盖每一个私有/小众的
> 事实。RAG 相当于"开卷考试"——考试之前先给它发一份相关的参考资料，让它照着资料回答，
> 而不是全凭脑子里的记忆（"闭卷考试"）。检索质量直接决定回答质量：如果检索回来的资料是
> 错的或者不相关的，模型大概率会被带偏（这也是为什么本项目 RL 环境的语料要专门设计
> "存在近似文档但答案唯一"这种难度，见第三部分）。

检索最基础的一种实现方式是 **BM25**（一种基于关键词的排序算法，本质是"词频 + 逆文档
频率"的加权打分，不涉及任何神经网络）：

> **大白话**：BM25 判断"这篇文档和这个查询有多相关"，核心直觉是——一个词在**这篇文档**里
> 出现得越多、但在**所有文档**里出现得越少（越"生僻"），这个词就越能代表这篇文档的特色，
> 匹配上这种词的文档应该排得更靠前。和"用向量做语义检索（Embedding + 余弦相似度）"是两条
> 不同的技术路线——BM25 不理解"同义词"（搜"汽车"匹配不到只写"轿车"的文档），但胜在
> **确定、可解释、不需要额外的模型**。本项目 `harness/corpus/index.py` 手写了一个 BM25
> 索引（而不是用现成的库），因为"索引本身就是环境定义的一部分"——见第三部分 3.1 节，
> 这是个很值得记住的工程决定。

## 1.8 从预训练到能对话：SFT 与 RLHF

一个刚训练完"预测下一个词"的模型（Base Model），并不会乖乖地按你的指令做事——它只是
"续写"，你给它一个问题，它可能续写出更多问题，而不是回答。要把它变成 ChatGPT 那种
"听得懂指令、愿意配合"的助手，通常要经过：

> **严谨定义**：**监督微调（Supervised Fine-Tuning，SFT）**指用一批"指令 → 期望回复"的
> 标注数据，对预训练模型继续训练，让它学会"人类希望它怎么回应"这种格式和风格。
> **基于人类反馈的强化学习（RLHF）**在 SFT 之后，用人类对多个候选回复的偏好排序训练一个
> "奖励模型"，再用强化学习（早期主要是 PPO）让模型去最大化这个奖励模型给出的分数，
> 进一步对齐人类偏好。
>
> **大白话**：预训练是"读遍全世界的文字，学会语言和知识"；SFT 是"手把手教它照着示范格式
> 回答问题"；RLHF 是"让它自己多次尝试回答，每次都有个评委（奖励模型）打分，它根据打分
> 调整自己的行为，越打越像人类喜欢的样子"。三个阶段一个比一个"贵"（预训练最贵最耗资源，
> RLHF 相对最省但最考验"怎么设计一个不会被投机取巧钻空子的评分标准"）。

本项目的 `rl/` 子系统做的正是"预训练/SFT 之后"的这一段——不是从零训练一个大模型，而是
拿一个现成的中小模型（`Qwen2.5-1.5B-Instruct`），先做一轮"拒绝采样 SFT"打底，再用强化学习
（GRPO）继续训练它"学会用检索工具做多跳问答"这件具体的能力（详见第三部分）。

## 1.9 强化学习基础：奖励、策略、优势函数

> **严谨定义**：强化学习（Reinforcement Learning，RL）里，**策略（Policy）**是"在某个
> 状态下该采取什么行动"的决策函数（这里策略就是 LLM 本身：给定上文，输出下一步该生成
> 什么）；**奖励（Reward）**是环境对一次行动/一整条轨迹给出的标量反馈；**优势函数
> （Advantage）**衡量"这次行动比'一般水平'好多少"，用它而不是直接用奖励原始值来更新策略，
> 能显著降低训练的方差。
>
> **大白话**：策略就是"模型这一次会怎么答"，奖励就是"这次答得好不好、打几分"，优势是
> "这次答得比它平时的平均水平好还是差"。强化学习的核心就是不断用"优势"这个信号去调整模型，
> 让它更倾向于做"优势为正"的事、更少做"优势为负"的事。

**PPO（Proximal Policy Optimization）** 是过去几年 RLHF 里最常用的算法，但它需要额外训练
一个"价值网络（Value Network）"去预测"这个状态下大概能拿多少奖励"，当作优势计算的基线，
这个额外网络本身要占显存、要调参，还可能训不准。

**GRPO（Group Relative Policy Optimization）** 是本项目 `rl/` 用的算法，思路是**不训练
价值网络**，而是对同一道题采样多条（比如 8 条）轨迹，**用这 8 条轨迹奖励的平均值当基线**
来算优势——详细展开见第三部分 3.5 节，这是面试 RL 岗位的高频考点。

## 1.10 KV Cache 与 Prompt 前缀缓存：为什么"顺序"和"要不要带秒级时间戳"很重要

> **严谨定义**：Transformer 推理时，生成每一个新 token 都要用到"之前所有 token 在每一层
> 算出来的 Key/Value 向量"；把这些向量缓存下来（KV Cache），生成下一个 token 时就不用把
> 前面所有 token 重新算一遍，只需要计算新 token 的部分。如果**两次请求的开头一段 token
> 完全相同**，这段的 KV Cache 也可以跨请求复用——这就是主流 LLM API 提供的"Prompt 前缀
> 缓存（Prompt Prefix Caching）"，命中的部分通常按更低价格计费，也算得更快。
>
> **大白话**：模型每次"思考"都要把输入从头到尾重新过一遍神经网络的计算，这个计算结果
> （KV Cache）如果两次请求开头一模一样，是可以"抄近道"复用的，不用重新算，还更便宜。
> 但只要开头有**哪怕一个字节的差异**（比如把系统提示词里的时间戳精确到秒、或者把工具在
> 请求里的排列顺序换了一下），这份缓存就整个失效，之前"抄近道"省下来的计算全部要重新
> 算一遍。

这就是为什么本项目：

- `harness/tools/registry.py::load_specs()` 扫描工具契约文件时坚持用 `sorted()`——
  保证工具在请求 `tools` 数组里的顺序稳定；
- 系统提示词只带**日期**、不带精确到秒的时间戳——README 给出的实测数字是这项优化能省下
  约 8000～9900 个输入 token；
- `rl/rollout/engine.py::run_many` 把同一道题的 G 条 rollout **刻意排在相邻的位置**——
  这 G 条轨迹共享从 system prompt 到第一个采样 token 之前的全部前缀，排相邻能让 provider
  命中前缀缓存的概率最大化，是一个"零成本"的吞吐优化。

有了这十节的预备知识，下面进入项目本身。

# 第二部分 · 项目全景导览

> 这一部分是 01～14 章的浓缩导览，每小节末尾标注对应详细章节。建议开着 `backend/` 目录
> 边看边对照代码。

## 2.1 项目是什么，为什么这么选技术栈

天启（Apocalypse）是一个单体应用：一个 FastAPI 进程既提供 REST/SSE API，也直接托管前端
静态文件。默认 SQLite，无前端框架（纯 HTML + 原生 JS）。这个选择本身就是一次"技术选型要
匹配项目规模"的示范——不是所有项目都需要拆成十几个微服务。

对求职最有含金量的，是里面的 **Harness 子系统**——一个自己实现的 Agent Runtime，
本教程后面 70% 的篇幅都在讲它。 → 详见 [01](01-技术栈总览.md)

## 2.2 后端分层：谁能依赖谁

```
routers  →  services | harness  →  models
    └──────────┴─────────┴──────────┴────→  core
```

`core` 是地基，不 import 任何业务模块；`services`/`harness` 是业务逻辑层，不碰
`Request`/`HTTPException`，只抛 `core/errors.py` 里定义的领域异常
（`ValidationError`/`NotFoundError`/`PermissionError_`/`UpstreamError`/`ConfigurationError`），
`main.py` 唯一一个异常处理器负责把它们翻译成 HTTP 状态码；`routers` 只做"解析请求 → 调
service → 返回 schema"，不写业务逻辑。这是"高层模块不该关心低层实现细节"这条原则的落地——
业务代码完全不知道"HTTP 状态码"这个概念存在。

配置的单一入口是 `core/config.py::Settings`，所有运行时目录（数据库文件、上传目录、
Harness 工作区……）都从一个 `VAR_DIR` 派生，这是"单一旋钮"设计，部署时只需要挂载一个
`./var` 卷做备份。

`core/sse.py` 那一行 `f"data: {json.dumps(payload)}\n\n"` 呼应第一部分 1.6 节讲的 SSE
协议——`data:` 后面的空格是协议要求，前端按固定 6 字符切片解析，删掉会导致前端解析全部
错位，是"看起来可以优化、实际上有跨文件契约"的例子。 → 详见 [02](02-后端分层架构.md)

## 2.3 前端：没有框架，靠约定维持可维护性

`utils → auth → api → ui` 固定加载顺序。`Auth.token()` 返回哨兵字符串 `'__cookie__'`
（因为真正的 JWT 是 `HttpOnly` Cookie，JS 读不到，这是故意的防 XSS 设计）。`apiFetch()`
是唯一和后端对话的入口，但它只返回 JSON——这直接导致**流式场景（SSE）必须绕开它、用裸
`fetch()`**，因为流式响应天生不是"等完整返回再解析 JSON"这种消费模型。这是"通用封装 vs
特殊场景"的典型权衡。 → 详见 [03](03-前端架构.md)

## 2.4 Harness 是什么：两条贯穿全局的不变量

从这里开始是全教程真正的核心。Harness 是部署在 `/harness.html` 的一个独立子系统，参照
`deepseek-ai/deepseek-harness` 的设计思想重新实现的**最小可用 Agent Runtime**——
把第一部分 1.5 节讲的"Function Calling 循环"工程化，加上人工审批、沙箱执行、完整可追溯
日志、上下文压缩、多智能体委派。这和 Claude Code、Cursor Agent 背后的核心机制是同一类
东西。

两条设计原则贯穿整个子系统：

**原则一：可替换的能力接缝（Replaceable Seams）**。四个关键组件——`SessionStore`
（会话存储）、`ModelAdapter`（模型适配器）、`Sandbox`（沙箱）、`ToolRegistry`（工具注册表）
——各自是"一个协议（Python `Protocol`）+ 一份默认实现"，全部在 `harness/context.py::
build_context()` 一处被装配起来。这是依赖倒置原则的教科书实践：高层模块（Agent 循环）
不依赖具体实现，两者都依赖抽象。

**原则二：全链路可追溯（Everything the Model Sees Is Logged First）**。发给模型的每一条
消息，必须先作为一个事件写进只能追加（append-only）的会话日志，然后才能被用来构造下一次
请求。`harness/session/projection.py::derive_messages()` 是**唯一**被允许把日志转换成
模型请求消息的函数。这条规则听起来多此一举，但它保证了"历史展示的内容"和"模型当时真实
看到的内容"永远一致——即使系统提示词本身会因为嵌入了当天日期而每天不同。

一次完整对话（Turn）的骨架：

```
turn/start
  step/start → assistant/chunk… → assistant/message → llm/usage
            → tool/call → [审批] → tool/result
  step/end  → （还有工具要调就再来一步）
turn/end
```

**Turn（轮次）**是用户发一条消息到模型给出最终回复的完整交互；**Step（步）**是 Turn 内部
"模型说一句话（可能带工具调用）→ 执行工具 → 结果喂回去"的一个循环单位。
 → 详见 [04](04-harness-总览与两大设计原则.md)

## 2.5 事件系统：`SessionEvent` 与投影函数

`SessionEvent` 是唯一的持久化数据结构（`type`/`seq`/`time`/`data`），`frozen=True` 让它
不可变——"让非法状态无法表示"原则的具体应用。19 种事件类型分两阵营：**只有** `user/message`、
`assistant/message`、`tool/result` 三种会被 `derive_messages()` 投影成真正发给模型的消息，
其余（`step/*`、`tool/call`、`llm/usage`……）只用于日志、重放、前端展示，不占用模型的
上下文窗口（呼应第一部分 1.2 节）。

`derive_messages()` 的核心逻辑：优先用日志里记录的系统提示词快照（而非当前配置现算），
叠加压缩摘要（如果有），逐条转换，并且**紧跟着每个 `tool_call` 去查找匹配的 `tool_result`
插入**——因为协议要求"一个带 `tool_calls` 的 assistant 消息，后面必须紧跟对应的 tool
消息"。如果某个调用因为审批中断而没有结果，会插入占位文本
`"[未完成：该工具调用被中断或取消]"`，否则大多数 provider 会直接拒绝这个请求。

会话"当前状态"（idle/running/awaiting_approval/error）是从日志**推导**出来的，不是一个
可以随意赋值的字段——`_turn_outcome()` 要在多种候选事件类型里找"时间最新"的那条，
不能只看最后一条，因为 `step/end` 是在 `tool/approval` **之后**才发出的（见 2.7 节）。

`reconcile_status`（3 分钟心跳窗口）+ `BackgroundTask` 清理（而不是依赖生成器 `finally`，
后者在客户端断连时不保证一定执行）+ 进程重启时 `reset_running_sessions()`，三层共同保证
"会话不会永远卡在运行中"。 → 详见 [05](05-harness-事件系统与会话存储.md)

## 2.6 Agent 执行循环：`run_turn()` / `_drive()`

`backend/harness/loop/agent.py` 的 `_drive()` 是整个系统的心脏，`for step in
range(max_steps)` 循环体依次：检查中断 → `PRE_STEP` 钩子 → 流式请求模型（对应第一部分
1.6 节讲的 SSE 消费）→ 落盘模型回复 → 判断有没有工具调用（没有就结束这个 Turn）→ 执行
工具调用 → 决定这一步是继续、暂停（等审批）还是结束。

`_request_model()` 里的流式分片**批量落盘**（`CHUNK_FLUSH_SIZE=32` 或
`CHUNK_FLUSH_SECONDS=0.15` 秒，任一条件触发就刷新一次）——实测每个 token 都单独写一次
数据库，能占掉一次长对话总耗时的约五分之一,这是"吞吐量 vs 实时性"的经典权衡。 → 详见
[06](06-harness-Agent执行循环.md)

## 2.7 工具系统与人工审批

**数据与代码分离**：一个工具由 `harness/data/tools/<模块>.json`（契约：名字、描述、
JSON Schema 参数、权限级别）和 `harness/tools/builtin/<模块>.py`（实现：`HANDLERS` 字典）
两个文件组成。契约没有匹配实现，启动时直接报错（快速失败）；实现没有匹配契约，只是死代码
（不报错）。

`load_specs()` 扫描契约目录时用 `sorted()`——直接呼应第一部分 1.10 节讲的前缀缓存原理：
工具在请求 `tools` 数组里的顺序必须稳定，否则会打碎 provider 的前缀缓存。

审批策略三档判定（`ApprovalPolicy.decide()`）：`read`/`write` 权限直接放行（因为路径已经
被强制收敛在工作区内，写坏了顶多是自己的工作区）；`exec` 权限（也就是 shell 命令）走白名单
三档——`denied`（`sudo`/`ssh`/`docker` 等，直接拒绝）、`auto_approved`（`ls`/`cat`/`grep`
等纯读取类，自动放行）、其余全部转人工（包括 `python`/`node`/`git`/`curl` 这些看起来
"平时都挺安全"但**能**执行任意代码或联网的命令）。判定标准是"能不能执行任意代码或打开
网络连接"，不是"看起来危不危险"。

子代理用 `StrictApprovalPolicy`——把 `ASK` 改写成 `DENY`，因为子代理内部弹出的审批卡片
永远不会有人能响应（主 Turn 正阻塞在等子代理返回结果这一步）。这没有放宽安全边界，
只是把"永远挂起"变成了"立即失败、附带原因"。 → 详见 [07](07-harness-工具系统与审批.md)

## 2.8 沙箱与安全边界：围栏，不是牢笼

沙箱防的是"模型自己犯的错"（被提示注入带偏），不是恶意管理员。三层边界：

- **命令执行走 `execve`**（`asyncio.create_subprocess_exec`），argv 数组直传，从头到尾
  没有 shell 会重新解释这个字符串，杜绝命令注入；
- **资源边界用 `setrlimit`**——CPU 时间、虚拟内存、文件大小都限制，但 `RLIMIT_NPROC`
  故意不设（因为它按操作系统真实用户 ID 统计，设低了会先饿死 Web 服务自己的正常进程）；
- **路径边界靠单一实现的 `contained_path()`**——`os.path.realpath()` 解析软链接防"曲线
  救国"，`startswith` 判断要拼上 `os.sep` 再比较，否则 `/root/workspaces/abc_backup`
  会被误判为 `/root/workspaces/abc` 目录下的路径。

容器层（Docker）再叠一层最小权限（`cap_drop: [ALL]`、非 root 用户、`pids_limit`）——
应用层挡"正常使用场景下模型犯错"，容器层挡"万一应用层某处逻辑真的被绕过了，损失面能封顶
在多低"，两层互补而不是重复。 → 详见 [08](08-harness-沙箱与安全边界.md)

## 2.9 技能系统：过程性知识按需注入

Skill 是一份"怎么做一件复杂事"的自然语言文档（可能带辅助脚本），系统提示词里只放**目录**
（名字+一句 description），正文靠模型主动调用 `load_skill` 工具按需读取。这个设计是为了
保住"全链路可追溯"不变量——如果做成"关键词命中就自动注入正文"，这次注入根本不会经过
`emit()` 写进日志，就会出现"模型确实看到了这段内容，但日志里查不到它是怎么来的"这种违反
核心不变量的情况。技能包的附带脚本会被**复制**进会话工作区的 `.skills/` 目录，而不是
放宽沙箱本身的访问规则。 → 详见 [09](09-harness-技能系统.md)

## 2.10 子代理：多智能体委派与花钱闸门

一个"委派"的本质是主 Agent 把某个子任务的完整执行过程交给独立的子 Agent，只关心它最终
返回的结论——好处是子任务的几十步中间过程不会挤进主对话的上下文窗口。四道花钱闸门（委派
深度、单会话次数、单次步数、墙钟超时）全部在真正发起前检查。`build_subagent_context()`
故意只传父会话的 `workspace`/`sandbox`，不传整个父 `HarnessContext`——最小知识原则
（Law of Demeter）的具体体现。费用统计必须递归汇总所有子会话——"实测一次派发里子代理花掉
的 token 比主 Agent 还多，分开算就会严重低估"。 → 详见 [10](10-harness-子代理多智能体.md)

## 2.11 一批"血泪教训"级工程细节

这一节浓缩全教程"最能体现真实踩坑经验"的内容：

- **流式 Function Calling 的分片拼接**：provider 只保证每个分片都带稳定的 `index`，
  `function.name` 往往只在第一片出现。`_ToolCallAccumulator` 按 `index` 聚合参数
  字符串，收完后名字仍为空就丢弃这个调用。
- **思考型模型的空回复陷阱**：一些推理增强型模型会先把输出预算花在"思维链"上，如果
  `max_tokens` 给小了，可能一个字正文都没写出来就被截断（`finish_reason == "length"`
  但 `content` 为空）。修复方式是**遇到这种情况直接抛异常**，绝不能悄悄当成"模型回复了
  空字符串"处理——这是"不要用一个看起来正常的默认值掩盖真正的异常状态"这条原则最典型
  的案例。
- **上下文压缩用真实 token 数，不用本地估算**：某次实测真实 `prompt_tokens` 是 9,874，
  本地估算只有 426，差二十多倍（因为本地估算漏算了系统提示词和全部工具 Schema 的固定
  开销，通常有 1500～2000+ token）。还有"拒绝无效压缩"的细节——预计收益低于阈值就直接
  拒绝并打警告，避免"越压缩越花钱却几乎没效果"的死循环。
- **未知价格显示"—"，不显示 0**——0 会让用户误以为"这次调用免费"。
- **系统提示词只带日期不带秒级时间戳**——呼应第一部分 1.10 节，实测省下约 8000～9900
  输入 token。

这些细节共同论证同一条原则：**决策依据要尽可能权威真实，异常状态不该被一个"看起来正常"
的默认值悄悄掩盖。** → 详见 [11](11-harness-成本上下文压缩与工程细节.md)

## 2.12 HTTP 接口与前端联调

`require_harness_user()` 功能整体关闭时返回 **404 而非 403**——不通过状态码差异暴露
"这个系统内置了一个 Agent 工作台"这个信息本身，是"最少暴露原则"的具体应用。

SSE 流式响应里，异常必须在生成器内部捕获、转换成"数据帧里的一个 `error` 字段"——因为一旦
响应头已经发出，HTTP 状态码就不可能再改变了。清理逻辑用 Starlette 的 `BackgroundTask`，
不是生成器的 `finally`（详见 2.5/2.6 节的解释）。

`/messages/derived` 接口调用的**跟循环内部真正用来发请求的是同一个 `derive_messages()`
函数**——不是另外写一份"展示用"的近似逻辑，这让"全链路可追溯"从一句自我标榜变成了用户
随时能在界面上点开核对的可验证事实。 → 详见 [12](12-harness-HTTP接口与前端联调.md)

## 2.13 部署与质量保障

两容器（`backend` + `nginx`）+ 单状态卷 `./var`。容器加固：`cap_drop: [ALL]`、非 root
用户 10001、`pids_limit`。`nginx.conf` 里 `proxy_buffering off` 和应用层
`X-Accel-Buffering: no` 是同一个目标的两道保险，保证 SSE 不被中间层攒批延迟。

没有 pytest——用 `tools/harness_check.py` 这类分阶段、可独立失败的探针脚本代替传统单测，
因为 Agent 系统的核心风险大多是"各组件真的接得上吗"这类集成层面的问题，探针脚本比 mock
掉外部依赖的单测更贴近真实故障面。 → 详见 [13](13-部署与验证.md)

## 2.14 第二部分小结：怎么把这些串成一句自我介绍

> "我做了一个自己实现的 Agent Runtime，核心是两条不变量——组件都套一层可替换的协议接口，
> 装配点只有一处；模型看到的一切必须先写进只能追加的事件日志，一个唯一的投影函数负责把
> 日志变成请求。在这个基础上实现了 Function Calling 的流式解析、基于命令白名单的人工审批、
> 进程级沙箱、按需读取的技能系统、带四道限制闸门的多智能体委派。"

更详细的问答对照见第四部分，以及 [14](14-面试准备指南.md)。

# 第三部分 · RL 工作台导览

> 这一部分把 Harness（一个能跑的 Agent）变成一个**能训练模型**的环境。如果你要投
> LLM Post-Train / Agentic RL 方向，这是含金量最高的部分。

## 3.1 Agent 运行时 ≠ RL 环境

第一部分讲过 RL 需要三样东西：动作空间、状态转移、奖励函数。Harness 已经有前两样
（工具 + 事件日志），**完全没有的是奖励函数、可复现性、任务集**。

一个运行时要变成环境，有一堆看起来矛盾的地方要改：联网必须关掉（否则今天和明天跑出的
结果不可比）、工具集必须锁死（多一个工具就是另一个任务）、系统提示词不能带日期（跨天
重新分词就不一致）、上下文压缩必须关（会在轨迹中途改写 system 消息，破坏训练需要的"前缀
稳定性"）、人工审批不能出现（rollout 没有人，会永久挂住）。

好消息是"可替换接缝"和"全链路可追溯"这两条不变量让这些改动都很小——整个环境只新增了
一个工具模块（`corpus`）、两个配置项，`agent.py`/`projection.py`/`events.py`/`context.py`
/`approval.py` 一行没改。"全链路可追溯"这条不变量在 RL 场景下价值翻倍——因为一条轨迹的
事件日志天然完整，`derive_messages()` 是唯一投影函数，几个月后重建的消息序列与当时发出去
的逐字节相同，这从源头掐掉了 **train/inference 不一致**（训练时构造的输入和采样时模型
真正看到的输入不完全相同）这一整类 bug。 → 详见 [15](15-rl-从Agent运行时到RL环境.md)

## 3.2 环境设计的第一版是怎么被数字推翻的

这是全课程最值得精读的一段。第一版设计：自建 5 万篇 arXiv 论文语料出题，"给出某篇论文的
改写描述，问它第一作者另一篇论文的编号"。实测发现——**在任何能从 arXiv 构建出来的语料上，
"按描述找到那篇论文"都是一步到位的**：取摘要最罕见的 8 个词去检索自身，top-1 命中率
100%；第二名的 BM25 得分只有第一名的 0.28（中位数），说明每篇论文都是一座孤岛，附近没有
可混淆的文档。换成 HotpotQA distractor split（每题自带 2 段 gold + 8 段专门检索出来的
干扰段）之后，这个比值变成 0.84，58% 的题存在强竞争者——难度必须来自**语料本身存在近似
文档**，这是语料的性质，改措辞改不动。

这一段值得在面试里主动讲：**"我先量了，发现环境不成立，然后改了设计"**，比"我做了一个
能跑的 benchmark"更能证明你有"判断一个环境是否有效"的能力。 → 详见
[15](15-rl-从Agent运行时到RL环境.md)

## 3.3 任务集与泄漏过滤：题目本身可能是假的

> **数据泄漏（leakage）**：模型不需要检索、单凭训练时记住的知识就能答对题目。这是唯一一种
> "所有仪表都正常（pass@1、reward、格式合法率全在涨）、但训出来的东西完全不是你要的"的
> 失败——因为它奖励了"跳过工具"这个行为。

测法是**闭卷问答**：题目原样问模型，不给任何工具，用**和真实 rollout 完全相同的验证器**
打分，提示词刻意鼓励猜、用强模型测，让结果成为**上界**。实测近一半的 HotpotQA dev
（49.8%，取两个模型的并集）能被闭卷答对，`comparison` 类型题（"A 和 B 哪个是……"）
尤其严重（64.8%），因为题面本身就把两个候选都写出来了。

**泄漏是 (题目, 模型) 的性质，不是题目的固有属性**——两个模型的泄漏集一致率只有 76.7%
且互不包含，所以必须取并集，只用一个模型筛会漏掉一部分真正泄漏的题。还有两个容易做错的
处理：空回复（思考型模型把输出预算烧在推理上）要记为"未知"而非"答不出来"，否则会把
本该丢弃的题误判成"安全"留在数据集里；覆盖不全的题（只被一个过滤器复核过）要一并丢弃，
否则过滤强度不一致会系统性抬高在它上面测出的指标。

最终漏斗：7405 道原始题 → 丢弃 49.8% 泄漏 + 12.1% 覆盖不全 → 保留 2824 道。这张漏斗表
本身就是最值得展示的产出物——它证明"你知道数据可能是假的、你去量了、你按量出来的数字做
了取舍"。 → 详见 [16](16-rl-任务集与泄漏过滤.md)

## 3.4 奖励与验证器：怎么把"做得好不好"变成一个不会被刷的数

结果奖励用**精确匹配**（归一化后的字符串相等），不用 LLM judge——三个理由：答案形态
适合（短跨度/年份/人名/yes-no）、确定且免费、judge 会随着自身版本升级悄悄漂移所有历史
数字。F1 只报告、不进入训练信号，因为部分给分会鼓励"多塞几个可能相关的词"这种对冲行为。

反作弊三条规则（编号出处校验、记忆作答检测、引用灌水检测），**命中即作废而不是打折**——
打折的话只要 outcome 那一项比折扣大，刷分依然有利可图，只有作废能让期望收益真正归零。
其中"记忆作答"规则在真实轨迹上抓到过一个假阳性：如果答案本身就出现在题面里（比如
comparison 题"A 还是 B"），模型检索它是完全正确的行为却被误判成"记忆作答"——这条规则
如果不修，会在训练里悄悄把 20% 的任务分布（comparison 题占比）判成零分,而且症状会伪装成
"策略就是不会做对比题"，容易被误诊到别的地方。修法是豁免"答案已出现在题面里"的情况。

**塑形项必须门控在正确性之后**是整个奖励设计里最容易毁掉一次训练的地方：如果奖励公式是
"outcome + 塑形项"直接相加，训练早期模型几乎从不答对，`outcome` 恒为 0，效率惩罚就成了
**唯一有梯度的项**，而最省力的最大化方式是"立刻空答、一次检索都不做"——策略会飞快学会
放弃，而且不可逆。解法是把所有塑形项**乘在 outcome 上**（只在答对的轨迹之间做区分，
答错精确得 0）。 → 详见 [17](17-rl-奖励与验证器.md)

## 3.5 分词对齐与 Loss Mask：多轮 RL 最难发现的一类 bug

这是全课程技术含量最高的一章。核心问题：**训练时算梯度的那些 token，必须和采样时模型
真正生成的那些 token 逐一对应**——这句话听起来是废话，但在多轮 Agent RL 里默认不成立，
而且不成立的时候**没有任何报错、loss 曲线还是平滑下降**，只能靠主动写断言去证明写对了。

两个具体根因：

1. **`arguments` 是原始 JSON 字符串，但 Qwen 的 chat template 会对它做 `| tojson`**——
   对一个字符串做 `tojson` 会把它变成一个"JSON 字符串的字符串"（双重编码），而 vLLM 的
   服务端会先归一化再套模板，导致 rollout 产出和本地重建产出的 token 序列每次工具调用
   都差若干 token。修法是在套模板前主动把 `arguments` 从 JSON 文本解析成对象。
2. **停止符 `<|im_end|>` 不在 mask 覆盖范围内**——如果 loss mask 不覆盖停止符，模型
   永远学不到"该在这里停"，训出来的结果是不停地说下去直到撞上 `max_tokens`。

根本解法是**让服务端彻底不碰模板**：本地用入库的模板文件（记录 sha256，防止 HuggingFace
原地更新模板导致历史轨迹失效）套模板拿到 token id，把整数序列发给 vLLM 的
`/v1/completions`（不做任何模板处理），自己解析 `<tool_call>{...}</tool_call>` 格式的
工具调用输出。这样"不一致"从"要小心的事"变成"结构上不可能发生的事"。

还有一处"断言先写错又改对"的过程很值得记：最初断言"每个消息边界处前缀都稳定"，在六条
真实轨迹上全部失败——原因是 Qwen 模板会把连续的 tool 响应合并进同一个 block，加入第二条
tool 消息时第一条的收尾标记会被移动，这是模板的正常行为，不是 bug。真正需要成立的更弱
条件是"**每个 assistant 轮的 prompt，是完整序列的前缀**"——没有任何 assistant 轮落在
tool 块内部，所以这条精确成立。这个过程说明"断言太强和断言太弱一样危险，得想清楚构造
真正依赖什么"。

实测每条轨迹只有 **7～12%** 的 token 是可训练的（其余都是系统提示词和工具观测，
mask = 0）——这个数字直接推出下一节 token 级归一化的必要性。 → 详见
[18](18-rl-分词对齐与loss-mask.md)

## 3.6 GRPO 与训练循环

GRPO（第一部分 1.9 节已定义）不需要价值网络，用同一道题 G 条 rollout 的均值当基线。
最重要的健康指标是 **`all_zero_groups`**——如果一组的 G 条奖励全一样（全对或全错），
组内标准差为 0，每条的 advantage 精确为 0，这一组贡献的梯度精确为零，**但它照样花掉了
G 条完整 rollout**，而 reward 曲线单独看不出这件事。

**token 级归一化 vs 按序列取平均**，可以用一个具体数字说清：一条 5-token 轨迹
（advantage +1）加一条 1-token 轨迹（advantage −1），token 级归一化结果是 -0.667，
按序列平均是 +0.000（两者恰好抵消）。结合上一节"可训练 token 只占 7～12%、长度差异很大"
的事实，按序列平均会系统性地低估长轨迹——而长程行为正是这个环境要训练的东西，所以选
token 级。

`logp_old` 必须在**采样那一刻**记录，不能事后用当前策略重算——否则 ratio 恒等于 1，
裁剪永远不触发，现象是"`clip_fraction` 一直是 0"，看起来反而像"训练很稳"。并发 rollout
完成顺序是乱的，`logp_old` 要按**prompt 前缀匹配**而非记录顺序配对，匹配不上就整条丢弃
（宁可退化成"第一步 on-policy"，也不要真假 ratio 混用）。

冷启动 SFT 不是可选项——1.5B 模型直接上手多跳检索几乎全错，每组全 0 分意味着从第一步起
梯度就精确为零。用强模型走同一套工具/环境采样、只保留通过验证器的轨迹（验证器同时是 RL
奖励和 SFT 数据过滤器）、按（题目, 工具调用序列）去重防止梯度被容易题主导。SFT 还顺带是
mask 构造的"金丝雀"——它和 GRPO 共用同一套 `pack()` 逻辑，mask 错一个 token 会让 SFT 
不收敛或产出乱码，在一次比 RL 便宜得多的运行上、响亮而且早地暴露问题。

在线难度课程用**运行中已有的 rollout 持续重估**通过率来决定一道题是否还活跃——静态
过滤会犯两个错：标定的是教师模型而非待训练策略的难度，以及"只标定一次"会扔掉自己未来
最好的数据（今天 0/8 明天变 3/8 的题，正是那时最该练的）。 → 详见
[19](19-rl-GRPO与训练循环.md)

## 3.7 Rollout 引擎与系统指标

实测 p50=9 秒、p95=236 秒——多轮 Agent rollout 的长尾是常态。批同步调度（`asyncio.gather`
分块跑）的墙钟上界是**每批最慢那条**，长尾场景下大部分时间并发在空转；连续补位（一个
信号量 + 三十行代码，任何一个 episode 结束立刻补进下一个）解决这个问题——**同时把批同步
方案也留在代码里**，专门用来产出"优化前后"的对照数字，而不是只凭主观判断说"这样更好"。

`utilisation`（并发占用率）和 `slowest_5pct_share`（最慢 5% 占总时长的比例）是两个能
直接对应行动的浪费度量。一条轨迹失败绝不能带走一整轮——`run_episode` 永不向上抛异常，
坏的那条记下 error 并计入失败率分母，其余继续跑，否则失败率会伪装成"样本量少一点"。

内存版 `SessionStore` 不只是图快——它绕开了 SQLite 实现里 `manager.create()` 需要真实
`users.id` 外键这个硬阻塞（一条 rollout 没有真实用户），代价是必须证明它和 SQLite 版
`derive_messages()` 的输出逐字节相同（自检里有专门的断言阶段）。 → 详见
[20](20-rl-Rollout引擎与系统指标.md)

## 3.8 第三部分小结

RL 这六章合起来最该拿出去的东西：语料 66,581 段带 sha256 可复现；任务漏斗 7405→2824；
arXiv→HotpotQA 的实测推翻（0.28→0.84）；精确匹配 + 三条反作弊命中即作废；塑形门控在
正确性之后；分词双重编码的解法（本地套模板 + 传 token id）；可训练 token 只占 7-12%；
token 级 vs 按序列归一化的具体数字（-0.667 vs +0.000）；p50/p95 长尾与连续补位；`rl_check`
20 个自检阶段。这些数字本身就是"我验证了什么"的清单，比任何形容词都有说服力。

# 第四部分 · 面试官视角 QA

> 这一部分不是"背答案"，是模拟一场真实面试里**面试官会怎么一路追问下去**。每一题给出：
> 面试官可能的开场问法、几层追问、一份"及格线回答"长什么样、一份"能让人眼前一亮"的回答
> 长什么样，以及一个常见的"踩坑式"回答（说明它哪里薄弱）。

## 4.1 开场：项目介绍与整体设计

**Q：介绍一下这个项目，重点讲讲你觉得最有技术含量的部分。**

- 追问 1："你说的'自己实现了 Agent Runtime'，具体是相对什么而言的？如果用 LangChain
  能做到同样的效果吗？"
- 追问 2："两条设计原则里，如果只能留一条，你会留哪条，为什么？"

**及格线回答**：能说出"Function Calling 循环 + 事件溯源存储 + 沙箱 + 审批"这几个组件
名字，能大致描述它们各自干什么。

**加分回答**：能讲清楚"可替换接缝"和"全链路可追溯"这两条原则**互相独立、但共同支撑同一个
目标**——前者是"系统内部各组件怎么互相解耦"，后者是"系统对外的行为承诺（模型看到的和
日志记录的永远一致）怎么被工程上保证"。能举出"如果只有 LangChain 帮你封装好 Function
Calling 解析，你答不出'流式场景下 tool_call 的 name 字段只在第一个分片出现'这种问题"作为
对比，说明自己写和调包的区别在于**能不能被继续往下追问**。

**常见踩坑**：只会说"我用了 XX 框架搭了一个 Agent"——这句话信息量几乎为零，因为框架把
所有细节封装掉了，面试官追问不出候选人真正理解了什么。

## 4.2 Function Calling 与流式解析

**Q：Function Calling 具体是怎么工作的？如果我现在让你手写一个（不用任何 SDK），你要处理
哪些边界情况？**

- 追问 1："流式响应下，工具调用是怎么一步步拼出来的？"
- 追问 2："如果 provider 没有返回工具调用的 `id` 字段怎么办？"
- 追问 3："模型的工具调用参数是合法 JSON 吗？如果不是呢？"

**及格线回答**：能画出"请求 1（带 tools）→ 模型返回 tool_calls → 服务端执行 → 请求 2
（带 tool 结果）→ 模型给出最终回复"这个两轮往返图。

**加分回答**：能讲清楚流式场景下 `index` 是唯一保证每个分片都带的字段，`function.name`
往往只在第一个分片出现，需要一个按 `index` 聚合的累加器把 `arguments` 字符串分片拼接
起来；能讲到"如果没有 `id` 就自己生成一个兜底 id"；能讲到"参数字符串解析失败要当成工具
执行失败处理、把错误信息作为文本喂回模型，而不是让整个请求崩掉"（工具失败是值，不是
异常）。

**踩坑回答**："我用官方 SDK，它帮我处理好了"——这句话在这个方向的面试里几乎等于交白卷,
因为它证明候选人从未真正深入过这一层。

## 4.3 安全与沙箱

**Q：你怎么让一个 Agent 敢用 shell 又不会把系统搞坏？**

- 追问 1："为什么不直接把整个 Agent 跑在一个 Docker 容器里就完事，还要在应用层做这么多
  事？"
- 追问 2："你刚才提到路径收敛要处理软链接，能具体讲讲怎么判断'越界'吗？"
- 追问 3："`RLIMIT_NPROC` 为什么不设？这不是应该设得越严格越好吗？"

**及格线回答**：能说出"execve 不走 shell，防命令注入""白名单三档判定"这两点。

**加分回答**：能讲清楚**为什么审批策略的判定标准是"能不能执行任意代码或联网"而不是
"看起来危不危险"**——`git`/`curl` 在 99% 场景下无害，但因为具备这个能力属性，宁可多问
人一次也不自动放行。能讲清楚路径收敛的具体漏洞模式：只查 `target.startswith(root)` 会
被"`/root/abc_backup`"这种"邻居目录"字符串前缀匹配骗过，必须拼上 `os.sep` 再比较；
`os.path.realpath()` 解析软链接防止"建一个指向 `/etc/passwd` 的软链接再读它"这种曲线
救国。能给出 `RLIMIT_NPROC` 反直觉的原因——它按**真实操作系统用户 ID** 统计，如果这个
沙箱子进程和 Web 服务本身共享同一个真实用户，设低了会先饿死服务自己的正常 worker 进程,
针对 fork 炸弹应该换一层更合适的机制（墙钟超时+杀进程组+容器 `pids_limit`）去处理。

**踩坑回答**：只会笼统地说"用了 Docker 隔离"——这没有回答"应用层为什么还要做这么多事",
说明候选人没有理解"纵深防御"不是"选一层做到位"，而是"每一层各自挡住不同的风险"。

## 4.4 可靠性与状态管理

**Q：如果用户中途把浏览器关了，Agent 还在执行怎么办？**

- 追问 1："为什么不能直接在流式响应生成器的 `finally` 里做清理？"
- 追问 2："如果后端进程本身崩溃重启了呢？"

**及格线回答**：能提到"要有一个兜底机制把状态改回空闲"。

**加分回答**：能讲清楚 Python 异步生成器在客户端断连时**不保证** `finally` 块一定会被
执行（可能被垃圾回收器延迟很久甚至永不清理），必须用 Starlette 的 `BackgroundTask`（框架
保证在响应流结束后一定被调度）；再补一层 `reconcile_status` 的心跳窗口兜底（3 分钟没
新事件就判定为僵尸会话）；再补进程重启时 `reset_running_sessions()`——"没有一次 Agent
对话能活得比启动它的进程还久"。能指出这是**三层独立的保护叠加**，而不是依赖其中任何一层
单独生效。

**踩坑回答**：认为"加个 `try/finally` 就够了"——这是一个真实存在、容易被想当然认为
"肯定没问题"的坑，能主动指出这个反直觉的事实本身就是加分项。

## 4.5 上下文管理

**Q：对话长了、超出模型上下文窗口了怎么办？**

- 追问 1："你怎么判断'什么时候该压缩'？"
- 追问 2："压缩的时候，切在哪个位置合适？为什么？"
- 追问 3："如果压缩本身没什么收益怎么办？"

**及格线回答**：能说出"用一个摘要替换掉早期的历史消息"。

**加分回答**：能讲清楚触发判断必须用 provider 返回的**真实** `prompt_tokens`，而不是
本地按字符数估算——本地估算漏算了系统提示词和全部工具 Schema 的固定开销（通常
1500~2000+ token），给出具体数字对比（9874 vs 426，差二十多倍）。压缩边界只能切在紧邻
一条 `user/message` 之前，因为这是唯一不会把某个 `tool_call` 和它对应的 `tool_result`
从中间切断的位置。还能讲"拒绝无效压缩"——预计压缩收益低于某个阈值时直接拒绝并打警告,
避免"预算设太低、每一步都触发压缩、却压不下多少 token"的死循环。

**踩坑回答**：只会说"设一个 token 数上限，超了就删掉最早的几条消息"——这忽略了"删掉的
消息如果切断了 tool_call/tool_result 配对，下一次请求会被 provider 直接拒绝"这个具体
后果。

## 4.6 多智能体

**Q：你怎么控制多智能体委派的风险和成本？**

- 追问 1："子代理能不能再委派子代理？为什么限制在这一层？"
- 追问 2："子代理内部如果也需要人工审批怎么办？"
- 追问 3："你说委派能让主对话上下文更干净，那委派是不是意味着总花费更低？"

**及格线回答**：能说出"有一些限制参数，比如最大委派深度、最大步数"。

**加分回答**：能讲清楚**为什么子代理不能走普通审批流程**——主 Agent 的这一次工具调用
（委派本身）正阻塞在等子代理返回结果，子代理内部如果弹出一张审批卡片，没有任何人能看到
或响应它，会造成结构性死锁；解法是子代理用严格版审批策略，把"本该问人"的情况直接判定为
拒绝，附带原因让子代理自己决定要不要换种方式重试——**这没有放宽任何安全边界，只是把
"永远挂起"变成了"立即失败"**。能纠正"委派更省钱"这个直觉——实测一次委派里子代理消耗的
token 经常超过主 Agent 本身，委派换来的是"上下文更干净"，不是"总花费更低"，所以费用统计
必须递归汇总所有子会话，否则会严重低估真实成本。

**踩坑回答**：把"委派"简单理解成"分而治之能省资源"——这是一个常见但不准确的直觉，
面试官如果追问具体数字，答不上来就会显得只停留在概念层面。

## 4.7 一个综合性的"深挖"问题

**Q：这个项目里，你觉得最值得称道的、贯穿全局的一条设计原则是什么？**

这题没有"标准答案"，考的是候选人能不能**跳出单个功能点，看到系统性的一致性**。

**加分回答的形状**：不讲某个孤立功能，讲一条在完全不同模块里反复出现的原则——比如
"不要用一个看起来正常的默认值掩盖一个真正的异常状态"：思考型模型空正文该报错、不该返回
空字符串；未知计费价格该显示"—"、不该显示 0；压缩收益太小该拒绝执行并警告、不该假装
执行了一次象征性压缩。这条原则在完全不同的三个模块里被独立应用，说明这不是碰巧写对了
一次，而是一条被主动坚持的工程纪律——这种"跨模块一致性"是判断一个系统"是否真的有设计
思路"的信号。

## 4.8 RL / Post-Train 方向

如果面试官转向 RL 方向，节奏通常是"环境设计 → 数据质量 → 奖励设计 → 训练算法 → 系统
工程"这五层依次往下问，每一层都在考"你是否量过、是否知道不这样做会怎么错"。

**Q：你的 RL 环境是自己设计的还是用现成 benchmark？**

加分回答按**时间顺序**讲：先讲第一版自建 arXiv 语料的设计动机，再讲它是怎么被实测数字
推翻的（第二名/第一名 BM25 得分比中位数只有 0.28，说明每篇论文都是"孤岛"），最后讲换成
HotpotQA 后同一测量变成 0.84。这个顺序本身就是答案的一部分——它证明的是"判断一个环境是否
有效"的能力，而不是"跑通了一个 benchmark"这件事本身。

**Q：怎么保证模型学的是检索能力，而不是背答案？**

加分回答讲闭卷测量的完整设计：提示词刻意鼓励猜、用强模型测（让结果成为上界）、两个模型
取并集（因为泄漏是"题目+模型"的性质，一致率只有 76.7% 且互不包含）、空回复算"未知"而非
"否定"、覆盖不全的题必须丢弃。能主动提到 comparison 题泄漏率（64.8%）远高于 bridge
（27.2%）的具体数字，以及为什么这是过滤器的**正确**副作用而不是 bug。

**Q：多轮场景下 loss mask 怎么算，踩过什么坑？**

这是整个 RL 部分技术含量最高的一题，值得主动展开讲三个具体坑：`arguments` 字符串被
模板 `tojson` 双重编码、停止符必须进 mask 否则模型学不会停止、以及"断言先写错又改对"的
过程（最初断言每个消息边界前缀稳定，六条真实轨迹全部失败，原因是 Qwen 模板会合并连续
tool 消息，真正该成立的是更弱的条件"每个 assistant 轮的 prompt 是完整序列的前缀"）。
能讲出这个"断言从错到对"的过程，比直接背出正确结论更有说服力——它证明候选人是真的调试
过，不是照抄文档。

**Q：为什么用 GRPO，token 级归一化和按序列平均有什么区别？**

直接给数字：一条 5-token 轨迹 advantage +1、一条 1-token 轨迹 advantage -1，token 级
归一化是 -0.667，按序列平均是 +0.000（恰好抵消）。多轮场景下这个偏差是系统性的，
一直在低估长轨迹，而长程行为正是要训练的东西。

**Q：怎么判断一次训练是健康的？**

先说明 reward 曲线单独看不出健康与否，再讲 `all_zero_groups`（组内奖励全同、advantage
精确为 0、但照样花了完整的 rollout，损失函数里一切正常，reward 曲线看不出）是最重要的
指标；再讲 `gave_up`（策略学会了"不答比检索更省力"）和 `voided`（策略找到了刷验证器的
办法）——**这两个可以和平均 reward 同时上升**，是这个环境里 reward hacking 和奖励崩塌
真正显形的地方。

**Q：这个项目有哪些地方没做完？**

这题**要老实答**，老实答本身是加分项。照实说明：环境、数据、奖励、分词对齐、GRPO
目标函数、训练循环编排都已经验证过，正式训练和消融实验还在等 GPU；`rl_check` 20 个阶段
全绿，但训练相关的几个阶段跑的是 stub hooks 验证编排逻辑正确，不是真实的
forward/backward。再解释**为什么按这个顺序**——分词对齐是唯一一种"看起来在训练、其实在
学噪声"的失败模式，必须在不需要 GPU 的机器上先验证到位，租卡之后只做已经调通的实验，
不在计费的资源上试错。这比含糊地说"训练还在跑"要扎实得多。

## 4.9 工程素养类问题（不针对某个具体模块）

**Q：这个项目为什么没有 pytest？你怎么保证质量？**

加分回答：这是主动选择，不是缺失。Agent 系统的核心风险大多是"各组件是否真的按预期顺序
接得上"这类集成层面的问题，用分阶段、可独立失败、能接入部署脚本的探针脚本
（`harness_check.py`）验证整条真实链路，比 mock 掉外部依赖的单元测试更贴近真实故障面。
能补充"每个阶段互相独立，一个失败不阻止其余继续跑，最后统一汇总报告"这个具体设计，
说明这不是"没时间写测试"的托辞，而是有意识选择的验证策略。

**Q：如果要把存储从 SQLite 换成别的数据库，或者让沙箱换成真正的容器级隔离，你会怎么改？**

这题在考"可替换接缝"理解得透不透。正确答案：**只改 `harness/context.py::build_context()`
这一处装配点**，新写一个实现对应 Protocol（`SessionStore`/`Sandbox`）的类，其余所有
代码因为只依赖协议类型、不依赖具体实现，完全不用改。能不能一口气说出"只改一处"，
而不是含糊地说"改一下存储层的代码"，是这题的分水岭。

**Q：第三方开源代码能不能直接拿来用？**

这是一道考"工程判断力是否包括合规意识"的题。可以讲这个项目里真实遇到的例子：
`anthropics/skills` 仓库公开的 docx/pptx 技能虽然代码可读，但附带的 `LICENSE.txt`
明确禁止"在 Anthropic 的 Services 之外保留副本"，不能直接搬进自建服务器；项目里的
docx/pptx 技能是独立实现，只依赖开源的 `python-docx`/`python-pptx`/`pandoc` 从零重写的
功能等价物。这是一个具体、真实、可核实的例子，比空泛地说"我会注意版权问题"有说服力。

## 4.10 反问环节：你可以问面试官的问题

- 不要试图记住所有细节。挑 3～5 个你觉得最能体现深度的点，准备到"能画图、能举反例、能

  归一化的那两个数字（-0.667 vs +0.000）。
