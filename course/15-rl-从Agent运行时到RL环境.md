# 15 · 从 Agent 运行时到 RL 环境

前面 14 章讲的是「怎么造一个 Agent 运行时」。这一章开始讲一件不同的事：
**怎么把它变成一个能训练模型的环境**。

这不是同一件事，差别也不是「再加个训练脚本」那么小。理解这个差别，是整个 `rl/` 部分的前提。

---

## 15.1 为什么 Agent 运行时不等于 RL 环境

> **严谨定义**：强化学习环境（environment）是一个可交互、可复现、能对行为给出标量回报的系统。
> 形式上它要提供三样东西：动作空间（agent 能做什么）、状态转移（做了之后世界怎么变）、
> 奖励函数（做得好不好）。
>
> **大白话**：运行时是「一台能开的车」，环境是「一条能反复跑、有秒表、每次起点终点都一样的赛道」。
> 车造好了不等于有赛道。没有赛道，你连「这次比上次快了没有」都答不出来。

Harness 已经具备的：动作空间（工具）、状态转移（工具执行 + 事件日志）。
**完全没有的**：奖励函数、可复现性、任务集。

把这三样缺的补上，才叫环境。而这三样恰好是 LLM Post-Train 岗位反复点名的东西——
Anthropic 的 Code RL 岗直接写「设计 RL 环境与任务、构建能刻画好坏的奖励信号与验证器」。

### 一个运行时距离一个环境有多远

| | Agent 运行时 | RL 环境 |
|---|---|---|
| 联网 | 要，`web_search` 是核心能力 | **绝对不能**，否则今天和明天跑出的结果不可比 |
| 工具集 | 越多越好 | **锁死**，多一个工具就是另一个任务 |
| 提示词 | 带当天日期很合理 | 带日期 = 数据集跨天失效 |
| 上下文压缩 | 长对话必需 | **必须关**（原因见第 18 章） |
| 人工审批 | 安全边界 | rollout 里没有人，会永久挂住 |
| 一次运行的产出 | 一次对话 | 一条**可回放、可重新打分**的轨迹 |

右边这一列每一格都是一个需要动手改的地方。好消息是 Harness 的两条不变量
（第 04 章）刚好让这些改动都很小——下一节说为什么。

---

## 15.2 两条不变量为什么正好是 RL 需要的

回忆第 04 章的两条设计原则：

1. **可替换的能力接缝**——`SessionStore` / `ModelAdapter` / `Sandbox` / `ToolRegistry`
   各是一个协议加一份默认实现，装配点只有 `harness/context.py`。
2. **全链路可追溯**——模型看到的一切必须先写进只能追加的事件日志，
   `derive_messages()` 是唯一的投影函数。

第二条的价值在 RL 场景下会翻倍：

> **严谨定义**：train/inference 不一致（train-inference mismatch）指训练时构造的输入序列
> 与采样时模型实际看到的序列不完全相同。它会让梯度作用在模型从未产生过的 token 上。
>
> **大白话**：你让模型做了一道题，然后按着**另一张试卷**给它打分改错。分数和改错都算得出来，
> 数值上一切正常，但学到的东西是错的。

因为「模型看到的一切先写日志」，一条轨迹的事件日志天然就是完整的；
因为 `derive_messages()` 是唯一投影函数，几个月后重建的 `messages` 与当时发出去的**逐字节相同**。
这一整类 bug 从源头就被掐掉了。

**这条论证只有在自己写过 runtime 的前提下才成立**，也是面试里最值得讲的一句话。
（注意诚实边界：这解决的是**消息层面**的一致；token 层面还需要第 18 章的断言兜住。）

第一条不变量让改动变得很小。整个环境只用了：

```
新增数据文件：harness/data/tools/corpus.json
              harness/data/presets/deepresearch.json
              harness/data/prompts/deepresearch.md
新增代码：    harness/tools/builtin/corpus.py
              harness/corpus/          （语料读取 + BM25）
改动：        tools/registry.py     +1 行（_MODULE_GATES）
              core/config.py        +2 个字段
```

`agent.py` / `projection.py` / `events.py` / `context.py` / `approval.py` **一行未改**。

## 15.3 环境设计的第一版，以及它是怎么被自己的实测推翻的

这一节是全课程我最建议精读的一节。不是因为设计有多巧，而是因为**它错了，而且是被数字推翻的**。

### 第一版设计

自建 5 万篇 arXiv 论文语料（摘要 + 结构化元数据），出这样的题：

> 「有一篇论文提出了〔改写过的方法描述〕。请给出该文第一作者的另一篇论文的编号，
> 该文提交到 cs.CL 且在下一个季度。」

想法是：第一跳是**文本**的（描述 → 论文），检索技能长在这里；
第二跳是**结构化**的（论文 → 作者/日期 → 目标），答案来自元数据所以验证器精确且免费。

听起来很合理。我当时也这么觉得。

### 实测

```
测量（50k arXiv 语料，200 个样本）                        结果
取摘要里最罕见的 8 个词去检索它自己                       top-1 100%，0.7 ms
先删掉全部语料罕见词，再取剩下最罕见的 8 个词             top-1 仍然 100%
第二名 / 第一名 的 BM25 得分比                            中位 0.28，无一例 >0.8
把语料收窄到单一主题（LLM / diffusion / RL）              更糟，比值降到 0.19
```

第三行是关键：**第二名只有第一名 0.28 的分数**。每篇论文在 BM25 空间里都是一座孤岛，
附近根本没有可混淆的文档。所以只要描述忠实到人类能认出是哪篇，BM25 也一定能认出。

第四行反直觉，值得想明白：

> **大白话**：把语料收窄成「全是 LLM 论文」，直觉上应该更难区分。实际更容易。
> 因为 BM25 靠 IDF 打分——主题词（"language"、"model"）在窄语料里变得到处都是、权重掉下去，
> 而这篇论文自己的特异词反而**相对更突出**了。

### 结论与改法

**在任何能从 arXiv 构建出来的语料上，「按描述找到那篇论文」都是一步到位的。**
难度必须来自**语料本身存在近似文档**——这是语料的性质，改措辞改不动。

换成 HotpotQA distractor split 后，同一组测量：

| | arXiv 50k | HotpotQA 66.6k |
|---|---|---|
| 第二名/第一名 得分比（中位） | 0.28 | **0.84** |
| 存在 >0.8 强竞争者的比例 | 0% | **58%** |

因为 HotpotQA 每道题自带 2 段 gold + 8 段**专门检索出来的可混淆干扰段**，
这正是 arXiv 语料缺的性质。

arXiv 的语料与构建器**仍然保留在仓库里**（`rl/corpus/fetch_arxiv.py`）——
它是这条结论的证据，不是废弃代码。

### 为什么这一段值得在面试里主动讲

「我先量了，发现环境不成立，然后改了设计」比「我做了一个能跑的 benchmark」有说服力得多。
前者证明你有**判断一个环境是否有效的能力**，而这正是环境设计岗位的核心能力。
反过来说：如果没量过这些数字，你根本不会知道自己的环境是空的。

## 15.4 环境的最终形态

**语料**：HotpotQA distractor dev split 的 66,581 个去重维基段落，
`sha256` 写进清单，rollout 期零网络。BM25 索引手写在 `harness/corpus/index.py`。

> 为什么不用 `bm25s` 或 Pyserini？因为**索引是环境定义的一部分**。
> 一次库升级悄悄改掉分词或打分，就会悄悄改掉任务，让之前所有数字失效。
> 一百行钉在仓库里，是更便宜的保证。

**三个动作**（`harness/data/tools/corpus.json`），全部 `permission: "read"`：

| 动作 | 返回 |
|---|---|
| `corpus_search(query, k≤10)` | 编号 + 标题 + 正文前 200 字，**不含 `meta`** |
| `corpus_open(doc_id)` | 标题、`meta`、正文全文 |
| `corpus_answer(answer, citations[])` | `stops_turn`，返回**不含正确性**的固定串 |

三个细节各自解决一个问题：

1. **全部 `read`**——`ApprovalPolicy.decide()` 对 `read` 无条件放行，
   所以 rollout 不会停下来等人。审批策略一行都不用改。
2. **`search` 不返回 `meta`**——`search` 与 `open` 的信息分割**就是第二跳**。
   把元数据索引进正文，两跳就会塌成一次查询（15.3 的教训）。
3. **`corpus_answer` 的回执不透露对错**——否则模型可以反复调用，
   把验证器变成一个免费的神谕。这是反作弊的第一道，成本是零。

**`stops_turn` 从哪来**：沿用 `exit_plan_mode` 的现成机制（第 07 章）。
注意 `agent.py` 里 `stops_turn` 只在工具**没报错**时才生效——
所以一条轨迹里可能有多次 `corpus_answer` 尝试，验证器要按「最后一次成功的」算分，
并对失败尝试扣分，否则格式报错就成了免费重试。

**门禁**：`_MODULE_GATES` 加一行 `"corpus": "harness_corpus_enabled"`，默认 `false`。
不加的话，`standard` 预设是 `tools: ["*"]`，线上站点的 Agent 会平白多出三个工具，
provider 的前缀缓存还会失效一次。

## 15.5 rollout 期怎么装配环境

`rl/env/build.py::build_env_context()` 直接构造 `HarnessContext` 这个普通 dataclass，
**不走 `build_context()`**。每一处差异都是训练的硬需求，不是偏好：

| 差异 | 为什么 |
|---|---|
| 提示词钉死，不含运行时块 | `runtime_context()` 带当天日期，跨天重新分词就不一致 |
| `context_budget` 设成不可达 | 关掉 compaction，它会在轨迹中途改写 system 消息（第 18 章） |
| store 换成内存实现 | 循环每步都重读整个日志，SQLite 是一次查询、list 是一次切片 |
| 所有 rollout 共用一个工作区 | corpus 工具从不写文件；每条轨迹建一个目录会留下十万个空目录 |

另外两个自检断言把上面两条钉住：`assert_no_compaction()` 查日志里有没有
`compaction/summary`，`assert_single_system_prompt()` 查提示词快照是不是恰好一个。
**查日志而不是信配置**——配置写对了但被别处覆盖，是很常见的事。

## 15.6 本章小结

- Agent 运行时缺三样东西才能变成 RL 环境：奖励、可复现性、任务集。
- Harness 的「先写日志 + 唯一投影函数」从源头消掉了一整类 train/inference 不一致 bug；
  「可替换接缝」让整个环境只需新增数据文件 + 一个工具模块 + 两处配置。
- 第一版环境被自己的实测推翻：BM25 下「按描述找论文」永远一步到位，
  难度必须来自语料本身存在近似文档。**这个过程比结果更值得讲。**
- 三个动作的每个设计细节都在解决一个具体问题：审批、两跳分割、验证器不被当神谕。
