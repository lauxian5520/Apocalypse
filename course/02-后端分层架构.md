# 02 · 后端分层架构

## 2.1 分层与依赖方向

```
routers  →  services | harness  →  models
    └──────────┴─────────┴──────────┴────→  core
```

> **严谨定义**：分层架构（Layered Architecture）要求每一层只能依赖"更底层"的模块，禁止反向依赖或跨层跳跃；
> 这里额外约定"单向依赖 + 同层高内聚低耦合"，并且**靠约定而非工具强制**（没有用 import-linter 之类的
> 静态检查工具去卡这条规则，纯靠代码 review 和团队纪律维护）。
>
> **大白话**：`core` 是地基，谁都能踩它，它不认识任何人；`routers`（HTTP 接口层）站在最上面，
> 只管"收请求、调服务、吐响应"，业务逻辑不该写在这一层；`services`/`harness` 是业务逻辑层，
> 能用数据库模型，但绝对不能直接碰 `Request`/`HTTPException`——这是为了让业务逻辑能脱离 Web 框架
> 独立测试、甚至未来换框架时业务代码不用大改。

### 各层职责一览

| 层 | 目录 | 能依赖谁 | 不能做什么 |
|---|---|---|---|
| `core/` | `backend/core/` | 谁都不依赖 | 不 import 任何业务模块 |
| `models/` | `backend/models/` | `core` | 只描述表结构和关系，不写业务逻辑 |
| `schemas/` | `backend/schemas/` | `core`/`models` | Pydantic 出入参契约，跨路由共享 |
| `services/` `harness/` | `backend/services/`、`backend/harness/` | `models`/`core` | 不 import `routers`，不碰 `Request`/`HTTPException`，报错要抛 `core/errors.py` 里的领域异常 |
| `routers/` | `backend/routers/` | `services`/`harness`/`schemas` | 不写业务逻辑，只做"解析请求 → 调 service → 返回 schema" |

`core/deps.py` 是这条规则里**唯一的例外**——它虽然在 `core/` 目录下，但它就是 HTTP 层的一部分
（FastAPI 的 `Depends()` 依赖注入函数必然要碰 `Request`）。项目里专门有一条注释解释了为什么要有这个例外：
以前 `routers/auth.py` 里的 `require_user` 被别的 router 直接 import，导致"router 依赖 router"的
耦合；抽出来放进 `core/deps.py` 后，所有 router 只依赖 `core`，不再互相依赖。

## 2.2 `core/` 各模块速览

### `core/config.py` —— 配置的唯一真相来源

```python
class Settings(BaseSettings):
    ...
    var_dir: str = ""
    sqlite_path: str = ""
    upload_dir: str = ""
    ...
```

`Settings` 继承 `pydantic_settings.BaseSettings`，会自动从项目根目录的 `.env` 文件读取同名环境变量。
关键设计是 `_resolve_runtime_paths()`（一个 `@model_validator(mode="after")`）：

> **严谨定义**：`model_validator(mode="after")` 是 Pydantic v2 提供的钩子，在模型的所有字段完成
> 常规校验、实例已经构造出来之后再执行一次自定义校验/加工逻辑，可以读取并修改多个字段之间的关联值。
>
> **大白话**：先把每个字段"各自"校验通过，再统一"扫一遍全局"做加工。这里的加工逻辑是：
> 如果 `sqlite_path`/`upload_dir`/`music_dir`/`feeds_dir`/`harness_dir` 这些字段留空，就用
> `var_dir` 拼一个默认路径出来。这意味着**只改一个 `VAR_DIR` 环境变量，就能把整个应用的所有状态
> 数据搬到别的地方**——这正是 README 里强调的"单一旋钮"设计。

`runtime_dirs` 是一个 property，把上面几个目录汇总成一个列表，`lifespan()` 在应用启动时遍历它挨个
`os.makedirs`。**给项目加一个新的运行时目录，只需要三步**：在 `Settings` 加字段、在
`_resolve_runtime_paths()` 的默认值字典里加一条、在 `runtime_dirs` 里加进去——这是 CLAUDE.md
明确写出来的规范，体现了"配置的单一入口"这个设计目标要靠代码约定持续维护，而不是加了字段就自动生效。

### `core/database.py` —— 引擎与会话工厂

用 SQLAlchemy 2.0 的 `DeclarativeBase` 作为所有 ORM 模型的公共基类；对 SQLite 单独注册了一个
`connect` 事件监听器，每次新建连接都执行：

```sql
PRAGMA journal_mode=WAL;
PRAGMA foreign_keys=ON;
```

> **大白话**：SQLite 默认不强制外键约束，也不是"预写日志（WAL）"模式。WAL 模式能让读操作不被写操作
> 阻塞（并发性更好），`foreign_keys=ON` 才能让 `ON DELETE CASCADE` 真正生效（比如删除一个会话，
> 它的所有事件行会跟着自动删除）。这两行 PRAGMA 是 SQLite 项目里很容易被忽略、但生产环境几乎必配的细节。

### `core/security.py` —— 认证的纯函数集合

这个模块**完全不碰数据库、不碰 `Request`**，只做三件事：密码哈希、JWT 编解码、Cookie 构造。

- **密码哈希**：`bcrypt` 对超过 72 字节的密码要么截断要么报错（版本相关），所以 `_clamp()` 先按 UTF-8
  安全边界主动截断，`password_error()` 提前用"最多 24 个中文字符"这类人类可读的提示做校验，而不是让
  用户提交后才收到一个底层库抛出的晦涩异常。
- **JWT**：`create_access_token(user_id, role)` 用 HS256 签名 `{"sub", "role", "exp"}`；
  `decode_access_token()` 捕获所有异常统一返回 `None`——**"解析失败"和"没登录"是同一种语义**，
  不需要在上层再分情况处理。
- **Cookie**：`set_auth_cookies()` 一次设两个 Cookie——JWT 本身是 `httponly=True`（JS 读不到，
  防 XSS 窃取），CSRF token 是 `httponly=False`（前端 JS 必须能读到它，才能在请求头里带回去做双提交校验）。

> **严谨定义**：CSRF 双提交校验（Double Submit Cookie）是一种防跨站请求伪造的机制：服务端下发一个
> 随机 token，同时写入一个非 HttpOnly Cookie 和期望前端在自定义请求头里回传；由于跨站页面能自动带上
> 目标站点的 Cookie，却读不到该 Cookie 的值（浏览器同源策略），也就没法伪造出匹配的请求头，从而校验通过
> 当且仅当请求确实来自能执行该站点 JS 的页面。
>
> **大白话**：光靠 Cookie 防不住 CSRF，因为浏览器会"自动"带上 Cookie，哪怕请求是从别的恶意网站发起的。
> 解决办法是"信息要分两路传"：一路走 Cookie（自动带），一路走请求头（只有真正加载了本站页面的 JS
> 才读得到 Cookie 里的值、才能手动塞进头里）。两路对得上，才说明请求是"知情"的。

### `core/deps.py` —— FastAPI 依赖注入

`require_user()` 先从 Bearer Token 或 Cookie 里取 token（`_token_from_request`），如果走的是 Cookie
认证，还要额外做 CSRF 校验（`_check_csrf`，对 `GET`/`HEAD` 等"安全方法"跳过校验，对 Bearer 认证也跳过——
因为浏览器不会自动附带 Bearer 头，跨站请求伪造不出来）。`require_admin()` 在 `require_user()` 基础上
再叠加一层角色检查。`optional_user()` 则**永远不抛异常**，专门给"游客也能看，登录了才能看到更多"这种
匿名友好场景用（比如笔记 Feed）。

### `core/errors.py` —— 领域异常词汇表

```python
class AppError(Exception):
    status_code = 400
class ValidationError(AppError):   status_code = 400
class NotFoundError(AppError):     status_code = 404
class PermissionError_(AppError):  status_code = 403
class UpstreamError(AppError):     status_code = 502
class ConfigurationError(AppError):status_code = 503
```

`services/` 和 `harness/` 只抛这几种异常，`main.py` 里**唯一**一个 `@app.exception_handler(AppError)`
负责把它们翻译成 HTTP 响应。这是"关注点分离"的直接体现——业务代码完全不知道"HTTP 状态码"这个概念，
它只知道"这是一个找不到资源的错误"，转换成 404 是路由层/框架层的事。

### `core/sse.py` —— 不能"顺手整理"的一行代码

```python
def sse(payload) -> str:
    return f"data: {json.dumps(payload, ensure_ascii=False)}\n\n"
```

这一行看起来可以"优化"，但**`data:` 后面那个空格是协议要求，前端 `line.slice(6)` 精确按 6 个字符
（`"data: "` 的长度）切片**，删掉空格会让前端解析全部错位。这是一个很好的例子，说明"看起来啰嗦的代码"
背后往往有一个跨文件、跨语言的隐性契约——改代码前先搜一下这行字符串在哪些地方被用到。

`SSE_HEADERS` 里还设置了 `X-Accel-Buffering: no`，专门用来关闭 nginx 的代理缓冲，配合
`deploy/nginx.conf` 里的 `proxy_buffering off`，双重保证流式响应不会被中间层攒批延迟。

### `core/providers.py` —— LLM 供应商配置的统一入口

`provider_config(name)` 根据 `AI_PROVIDER` 环境变量返回 `{url, key, model, format}`，支持
deepseek/gemini/zhipu/openai/ollama/custom 六种。`ai_service.py`（精灵聊天用）和 `harness/llm/*`
（Agent 工作台用）**共用这一份 provider 配置**，避免两套"供应商地址怎么拼"的逻辑各写一份、日后改一个
忘了改另一个。

## 2.3 `models/` 与迁移策略

`models/__init__.py` 把所有 ORM 类都 import 一遍，**纯粹是为了触发 SQLAlchemy 的 mapper 注册**——
这是一个很多初学者会踩的坑：如果某个模型类没被 import 过，SQLAlchemy 根本不知道它的存在，
`Base.metadata.create_all()` 就不会为它建表。

`models/migrations.py` 里 `init_database()` 做两件事：

1. `Base.metadata.create_all(bind=engine)`——处理**全新的表**，只要模型类被正确 import，这一行就够了。
2. 遍历 `_ADDED_COLUMNS`（一个 `{表名: {列名: DDL类型}}` 的字典）——处理**已经部署到生产环境、
   后来又加了新列**的表，用 `ALTER TABLE ... ADD COLUMN` 补齐。

> **大白话**：这不是 Alembic 那种"版本化迁移"（生成一串 `upgrade()`/`downgrade()` 脚本，能精确回滚到
> 任意历史版本），而是一个更轻量的"幂等补丁"——每次启动都检查一遍"这张表该有的列都有了吗，没有就加上"。
> 对个人项目/小团队来说，这种方案维护成本更低；代价是没法回滚、没法表达"删列""改类型"这类复杂变更。
> 面试时如果被问"为什么不用 Alembic"，可以诚实地说这是"够用就好"的取舍，而不是没有能力用。

## 2.4 `main.py` —— 应用装配

```python
app.include_router(api_router)      # 先挂 API
app.mount("/", StaticFiles(...))    # 最后挂静态文件
```

**顺序不能反**：`Mount("/")` 会匹配一切路径，如果它注册在 API 路由之前，所有 `/api/...` 请求都会被
静态文件服务器截胡，返回 404（因为静态目录下没有叫 `api` 的文件）。这是路由匹配顺序敏感性的典型例子。

`lifespan()`（FastAPI 的应用生命周期钩子）在启动时依次做：初始化数据库 → 创建所有运行时目录 →
`reset_running_sessions()`（把所有还标记为"运行中"的 Harness 会话状态修正为"空闲"，因为"没有一次
Agent 对话能活得比启动它的进程还久"——上次进程被杀掉时，这些会话就被腰斩了）→ 若 Feed 缓存为空则
触发一次异步抓取 → 启动定时任务调度器。

## 2.5 小结：这套架构解决了什么问题

- **可测试性**：`services`/`harness` 不依赖 Web 框架，理论上可以脱离 HTTP 直接单测（虽然这个项目
  实际用的是 [13-部署与验证.md](13-部署与验证.md) 里讲的探针脚本，而非 pytest）。
- **可替换性**：数据库类型、AI 供应商、运行时数据目录，全部是配置项而非硬编码。
- **单一职责边界**：出了 Bug，看异常类型就知道大概是哪一层的责任——领域异常来自业务层，HTTP 状态码
  的翻译只发生在 `main.py` 一处。

这套分层思路在 Harness 子系统内部被**再应用了一次**（`harness/` 自己也有 loop/session/tools/sandbox
的分层），下一章开始详细拆解。
