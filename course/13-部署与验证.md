# 13 · 部署与验证

## 13.1 部署形态

```
docker-compose.yml
├── backend  (deploy/Dockerfile 构建)
│   └── 挂载 ./var:/app/var  ← 唯一的状态卷
└── nginx    (nginx:alpine)
    ├── 挂载 ./frontend（只读）
    └── 挂载 deploy/nginx.conf
```

- **两个服务**：`nginx` 对外暴露 80/443，托管前端静态文件、反代 `/api/` 给 `backend`；
  `backend` 同时也直接对外暴露 8000 端口（方便调试/直连），生产环境正常流量走 nginx。
- **单一状态卷 `./var`**：数据库文件、上传文件、音乐、抓取缓存、Harness 工作区全部在
  这一个目录下——备份/迁移只需要打包这一个目录，这正是 [02](02-后端分层架构.md) 讲的
  "VAR_DIR 单一旋钮"设计在部署层面的体现。

### `deploy/Dockerfile` 里几个值得注意的细节

- 基础镜像 `python:3.11-slim`，装了 `gcc libpq-dev libffi-dev libjpeg-dev
  fonts-dejavu-core`。前四个是编译 Pillow/psycopg2 这类带 C 扩展的库需要的构建工具；
  最后一个是因为**基础镜像本身不带任何字体**，验证码生成如果没有可用字体，会退化成
  Pillow 内置的、几乎无法辨认的位图字体。
- **`fonts-dejavu-core` 不含中文字形（CJK glyphs）**——这意味着即使装好了 LibreOffice
  用来渲染 pptx 缩略图，中文幻灯片依然会渲染成"豆腐块"（方块乱码）。这是一个 CLAUDE.md
  专门强调的、容易被忽略的连带因果关系：**装对了软件（LibreOffice）不代表功能就完整了，
  还要装对配套的资源（中文字体）**。
- 先复制 `requirements.txt` 单独跑一次 `pip install`，再复制其余代码——这是 Docker
  分层缓存的标准技巧：只要依赖列表没变，重复构建时这一层可以直接复用缓存，不用每次
  改一行业务代码就重新装一遍所有依赖。
- 非 root 用户 `app`（uid=10001）运行，`chown -R app:app /app`，`USER app`——
  注释明确点出原因："harness 会代表模型执行命令，所以这个进程不能是 root"。
  部署时宿主机 `./var` 目录也必须 `chown` 成同一个 uid，否则容器内非 root 用户
  没有权限写入挂载进来的卷。

### `deploy/nginx.conf` 里和 SSE 相关的几行

```nginx
location /api/ {
    proxy_pass http://backend:8000;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
    proxy_buffering off;      # ← 和 core/sse.py 的 X-Accel-Buffering: no 呼应
    proxy_cache off;
}
```

`proxy_buffering off` 和后端应用层 `X-Accel-Buffering: no` 响应头是"同一个目标的两道
保险"——即使后端忘了设置那个响应头，nginx 配置本身也已经全局关闭了缓冲，SSE 流式响应
不会被反向代理攒批延迟。`proxy_read_timeout 300s` 设得比默认值宽松很多，因为一次
Harness 对话可能连续跑好几分钟（尤其是委派了子代理、又跑了好几步工具调用的情况），
默认的几十秒超时会把一个正常进行中的长对话直接掐断。

## 13.2 没有 pytest，靠什么保障质量

`requirements.txt` 里没有 pytest。这不是"疏忽"，而是这个项目实际选择的质量保障策略——
**用一组"探针脚本"（Probe Scripts）替代传统单元测试套件**，放在 `tools/` 目录下。

> **面试话术**：面试官如果问"这个项目怎么做测试"，诚实的回答不是"没写测试，来不及"，
> 而是"这个项目用分阶段的连通性探针脚本代替了传统单测——因为 Agent 系统的核心风险
> 大多是'各个组件真的接得上吗、真的按预期的顺序工作吗'这类集成层面的问题，用一组
> 能真实跑通整条链路的脚本，比大量 mock 掉外部依赖的单元测试更能直接发现问题"。
> 能讲清楚"为什么选择这种验证方式，而不是没有能力写单测"，比死记硬背"这里没有测试"
> 更能体现工程判断力。

### `tools/ai_probe.py`：最小的一个，只验证非 Harness 的 AI 供应商连通性

检查 `provider_config()` 解析出来的地址/Key 是否存在，然后分别用非流式（`chat()`）和
流式（`chat_stream()`，累计接收到超过 50 个字符就提前停止）各跑一次真实调用，
打印 PASS/FAIL。和 Harness 完全无关，只测精灵聊天用的那条独立 LLM 客户端链路
（见 [02](02-后端分层架构.md) 里 `ai_service.py` 和 `harness/llm/*` 是两套独立实现
的说明）。

### `tools/harness_check.py`：Harness 的多阶段连通性自检，共约 600 行

设计核心是一个 `stage(name, fn)` 包装函数——**每一个检查阶段互相独立，一个阶段失败
不会阻止后面的阶段继续跑**，最后统一汇总一份"哪些通过、哪些失败"的报告，一次运行
就能定位问题出在链路的哪一环。三种运行模式：

```bash
python ../tools/harness_check.py --offline      # 只测本地接线，不花任何 LLM token
python ../tools/harness_check.py                # 加上真实的 provider 调用
python ../tools/harness_check.py --url http://localhost:8000 --token <管理员JWT>  # 加上完整 HTTP/SSE 往返
```

按顺序检查：配置 → 数据库（建表后确认 `harness_sessions`/`harness_events` 两张表存在）
→ 沙箱与路径收敛（**专门测试 `../../etc/passwd` 和 `/etc/passwd` 都必须被
`workspace.resolve()` 拒绝**——CLAUDE.md 原话"containment is the whole point"，
安全边界不是"写完就该相信它对"，而是要有一个脚本每次都真正跑一遍越界尝试去验证它确实
在拦截）→ 工具注册表 → 审批策略（放行/询问/拒绝三档判定分别验证一遍）→ 事件日志与
消息投影 → 真实模型调用 → 工具调用的流式拼装 → 完整走一轮对话 → HTTP 接口与 SSE。
**全部通过退出码 0，任何一项失败退出码 1**——这个设计使得它可以直接接入部署脚本，
作为"这次部署是否健康"的一道自动化闸门，而不只是开发者手动跑着看结果。

这个文件本身几乎 import 了 harness 子系统的每一个公开模块——它同时也是一份很好的
"这个子系统对外暴露了什么"的阅读地图，如果要快速了解某个模块该怎么被外部正确使用，
看 `harness_check.py` 里怎么调用它，往往比翻文档更直接。

### `tools/harness_probe.py`：跑一整轮真实对话，不经过浏览器、不经过 HTTP

```bash
python ../tools/harness_probe.py --prompt "在工作区建一个 hello.txt 写入当前时间，然后读回来"
```

用一个专门的、**默认禁用登录**的探针账号（`__harness_probe__`，`is_disabled=True`，
密码哈希是一个不可能匹配的占位值"!"——保证这个账号永远不能真的登录进去，只用来
挂靠探针脚本创建的会话），直接在 Python 里调用 `build_context()` + `run_turn()`，
逐条打印每一个产生的事件（用一个按事件类型分发的格式化字典 `_DETAIL`），
最后打印投影出的消息列表和用量汇总。**如果这一轮卡在了"等待人工审批"**，脚本会打印
"本轮停在人工审批处——这是策略生效，不是失败"，而不是把这种情况当成一次异常/失败——
这和 [07](07-harness-工具系统与审批.md) 讲的"审批策略是安全机制，不是 Bug"是同一种
认知：**探针脚本的判定逻辑要理解被测系统的业务语义，不能简单粗暴地"只要停下来就是
失败"**。

默认跑的 prompt 特意设计成"写文件 → 读文件"这样一个最小但完整的端到端流程——既验证
了 `write` 工具，又验证了 `read` 工具，还顺带验证了沙箱路径收敛没有拦错正常操作。
`--keep` 参数可以保留这次探针跑出来的会话和工作区，供事后人工检视。

## 13.3 首次部署 checklist（面试可以当"我知道生产环境要注意什么"的加分项）

1. `cp .env.example .env`，务必修改 `JWT_SECRET`（同时用于登录签名和验证码校验）。
2. 填好 AI Provider 的 Key，用 `python ../tools/ai_probe.py` 单独验证 Key 是否有效——
   不要等到真正跑起 Harness 才发现是 Key 的问题。
3. Docker 部署前 `sudo chown -R 10001:10001 ./var`，否则容器内非 root 用户没权限写
   挂载进来的卷。
4. 生产环境 `COOKIE_SECURE=true` 并配好 HTTPS——否则认证 Cookie 会以明文形式在网络上
   传输。
5. `HARNESS_REQUIRE_ADMIN` 保持默认的 `true`，公网部署千万不要关掉。
6. 如果要开 `HARNESS_SHELL_ENABLED=true`，先完整读一遍 [08](08-harness-沙箱与安全边界.md)——
   README 原话："从那一刻起，审批提示承担了全部风险，不要靠削弱它去补偿"。
7. 部署完跑一遍 `harness_check.py`（带 `--url` 和管理员 token 的完整版），确认整条链路
   （包括真实 HTTP/SSE）都通。

## 13.4 本章小结

- 部署是"nginx + backend"两容器 + 单状态卷的简单形态，容器加固（非 root、丢弃
  capabilities）是安全模型的最后一层。
- 没有 pytest，用分阶段、可独立失败、可接入部署脚本的探针脚本代替——这是"用集成验证
  替代单元测试"的一种真实、可自辩护的工程选择，不是能力缺失。
- 部署 checklist 里每一条都能追溯到前面章节讲过的具体机制，说明"知道怎么部署"和
  "理解这套系统的安全模型"是同一件事的两个侧面。
