# 14 · 面试准备指南

这一章把前面 13 章的内容，整理成"一句话介绍 → 追问 → 参考回答思路"的对照表，
方便你在面试前快速过一遍、临场组织语言。**建议不要死记硬背下面的文字，而是确保
你能用自己的话把每一个"参考回答思路"复述出来**——面试官追问细节时，能不能接得住，
才是真正的分水岭。

## 14.1 三十秒自我介绍模板

> "我做了一个部署在个人网站上的开源项目，里面自己实现了一个 Agent 工作台，参照了
> DeepSeek Harness 的设计思想重写。它不是简单调用一个 API 拼 Demo，而是从裸的 HTTP
> 请求开始，自己实现了完整的事件溯源式会话存储、Function Calling 的流式解析、
> 基于命令白名单的人工审批机制、进程级沙箱隔离、按需读取的技能系统，以及带四道限制
> 闸门的多智能体委派。我可以详细讲讲其中任何一部分的具体设计权衡。"

## 14.2 高频问题与参考回答思路

### Q1：介绍一下你这个 Agent 系统的整体架构

> 参考思路：先说两条贯穿全局的设计原则——"可替换的能力接缝"（四个协议 + 默认实现，
> 一处装配点）和"全链路可追溯"（模型看到的一切必须先写进只能追加的事件日志，
> 有唯一一个投影函数负责把日志变成请求）。再画一下一个 Turn 的事件流程图
> （`turn/start → step/start → ... → step/end → turn/end`）。详见
> [04](04-harness-总览与两大设计原则.md)。

### Q2：Function Calling 具体怎么实现的？流式响应下的 tool_call 怎么解析？

> 参考思路：讲清楚"工具契约"（JSON Schema）和"handler 实现"分离存放；讲清楚 provider
> 流式返回 tool_call 时**分片**发送，只有 `index` 字段保证每片都有、`name` 往往只在
> 第一片出现，用一个按 `index` 聚合的累加器把参数字符串拼完整。详见
> [07](07-harness-工具系统与审批.md)、[11](11-harness-成本上下文压缩与工程细节.md)。

### Q3：怎么让 Agent 敢用 shell 又不会搞坏系统？

> 参考思路：分三层——① 命令解析走 `execve`，argv 数组直传，绝不经过 shell 解释，
> 杜绝命令注入；② 白名单三档判定（自动放行/转人工/直接拒绝），判定标准是
> "能不能执行任意代码或联网"，不是"看起来危不危险"；③ 资源边界用 `setrlimit`
> （要提到 `RLIMIT_NPROC` 故意不设的反直觉细节，这个细节很能体现深度）；
> ④ 路径边界靠单一实现的、能解析软链接的 `contained_path()`。详见
> [08](08-harness-沙箱与安全边界.md)。

### Q4：如果用户中途关掉浏览器，Agent 还在跑怎么办？

> 参考思路：讲清楚"异步生成器的 `finally` 不可靠"这个反直觉的事实，以及为什么
> 用 Starlette 的 `BackgroundTask` 才能保证清理逻辑一定执行；再补一层
> `reconcile_status` 的心跳窗口兜底（3 分钟没新事件就判定为僵尸会话，强制拉回空闲）；
> 再补进程重启时 `reset_running_sessions()` 的兜底。详见
> [05](05-harness-事件系统与会话存储.md)、[12](12-harness-HTTP接口与前端联调.md)。

### Q5：上下文超长了怎么处理？

> 参考思路：触发条件用 provider 返回的**真实** `prompt_tokens`，不是本地估算——
> 讲一下真实数字对比（9874 vs 426，差二十多倍，因为本地估算漏算了系统提示词和
> 工具 schema 的固定开销）。压缩边界只能切在紧邻一条 user 消息之前，避免把
> tool_call 和它的结果切断。还有一个"拒绝无效压缩"的细节——收益低于阈值时直接
> 拒绝压缩并打警告，避免陷入"越压缩越花钱却没效果"的死循环。详见
> [11](11-harness-成本上下文压缩与工程细节.md)。

### Q6：为什么需要"人工审批"这个环节，怎么设计的？

> 参考思路：这是 Human-in-the-loop 的具体实践——不是所有工具调用风险都一样，
> read/write 因为路径已经被强制收敛在沙箱内所以直接放行，只有"可能执行任意代码或
> 联网"的命令才需要人来判断，判定标准写在一份数据文件（白名单）里，能在代码之外
> 单独维护。详见 [07](07-harness-工具系统与审批.md)。

### Q7：多智能体委派会不会失控？怎么控制风险和成本？

> 参考思路：四道闸门（深度/次数/步数/墙钟），全部在真正发起前检查，深度限制
> 同时体现在内置角色的工具清单里（不给 `subagent` 这个能力）；子代理内部审批策略
> 是严格版——本该转人工的直接拒绝，因为主 Turn 正阻塞在这次调用上，没人能响应
> 子代理弹出的审批卡片；子代理只共享工作区和沙箱，其余组件独立重建；一次委派消耗的
> token 经常超过主 Agent 本身，费用汇总必须递归包含所有子会话。详见
> [10](10-harness-子代理多智能体.md)。

### Q8：这个项目里你觉得最有技术含量/最值得讲的设计是什么？

> 参考思路：不要只讲某一个孤立功能，讲一条贯穿全书的设计原则——"不要用一个'看起来
> 正常'的默认值掩盖一个真正的异常状态"：思考型模型空正文该报错不该返回空字符串，
> 未知价格该显示"—"不该显示 0，收益太小的压缩该拒绝不该假装执行。这条原则在完全
> 不同的模块里反复出现，说明这不是碰巧写对了一次，而是一条被主动坚持的工程纪律。
> 详见 [11](11-harness-成本上下文压缩与工程细节.md) 的小结。

### Q9：为什么系统提示词只带日期，不带精确时间？

> 参考思路：Prompt 前缀缓存——只要请求开头一段内容逐字节一致，provider 就能复用
> 之前算过的中间状态，按更低价格计费；带秒级时间戳意味着每次请求都不同，缓存立刻
> 失效。给出实测数字（约省 8000~9900 输入 token）。精确时刻改由一个不联网、
> 本地读取的 `current_time` 工具按需提供。详见
> [11](11-harness-成本上下文压缩与工程细节.md)。

### Q10：这个项目为什么没有 pytest？你怎么保证质量？

> 参考思路：诚实说明这是主动选择而不是缺失——Agent 系统的核心风险大多是"组件间
> 集成是否真的按预期工作"，用分阶段、可独立失败、能接入部署脚本的探针脚本
> （`harness_check.py`）验证整条真实链路，比 mock 掉外部依赖的单测更贴近真实故障面。
> 详见 [13](13-部署与验证.md)。

### Q11：如果要把存储从 SQLite 换成别的数据库/让沙箱支持真正的容器隔离，你会怎么改？

> 参考思路：这是在考"可替换接缝"设计理解得透不透——正确答案是"只改
> `harness/context.py::build_context()` 这一处装配点，新写一个实现对应 Protocol
> （`SessionStore`/`Sandbox`）的类，其余所有代码因为只依赖协议类型、不依赖具体实现，
> 完全不用改"。详见 [04](04-harness-总览与两大设计原则.md)。

## 14.3 反问环节可以问面试官的问题（体现你真的在思考 Agent Infra 这个方向）

- "贵司的 Agent 系统里，审批/人工介入的粒度是怎么设计的？是像这个项目一样按命令白名单
  判定，还是有更细的风险评分机制？"
- "上下文压缩策略是基于本地估算还是 provider 真实返回的 token 数？有没有遇到过因为
  估算偏差导致压缩时机不准的问题？"
- "多智能体委派场景下，子 Agent 的权限边界是怎么划的？有没有专门处理过'子 Agent 内部
  需要人工审批但没人能响应'这类结构性死锁？"

这些问题的提出本身，就是在向面试官展示——你不是刚看了这个项目的 README 临时准备的，
而是真的理解了这些设计背后要解决的通用问题。

## 14.5 RL 方向的追问（对应 15～20 章）

投 Post-Train / Agentic RL 岗的话，下面这些比 Q1～Q8 更可能被问到。

### Q9：你的 RL 环境是自己设计的还是用现成 benchmark？

> 参考思路：**两个都讲，而且按时间顺序讲**。先说第一版是自建 arXiv 语料 + 元数据推导答案，
> 然后说它是怎么被自己的实测推翻的——「摘要最罕见 8 个词检索自身 top-1 100%，
> 第二名只有第一名 0.28 分，收窄语料反而更糟（IDF 的缘故）」。结论是难度必须来自
> **语料本身存在近似文档**，这是语料的性质而非措辞能改的。然后说换成 HotpotQA
> distractor 之后同一测量变成 0.84、58% 有强竞争者。
> **这个顺序很重要**：它展示的是「判断一个环境是否有效」的能力，
> 而不是「我跑通了一个 benchmark」。详见 [15](15-rl-从Agent运行时到RL环境.md)。

### Q10：怎么保证模型是在学检索，而不是在背答案？

> 参考思路：讲闭卷测量。做法是把题原样问模型、不给工具、用同一个验证器打分；
> 提示词刻意鼓励猜不鼓励拒答，并且用强模型测，让结果成为**上界**。
> 实测近一半 HotpotQA dev 泄漏（comparison 题 64.8%，因为题面就写了两个候选）。
> 然后讲**一个模型不够**：两个模型一致率只有 76.7% 且互不包含，
> 所以泄漏是 (题目, 模型) 的性质，必须取并集。
> 再补两个易错处理：空回复是「没有结论」不是「答不出来」；
> 覆盖不全的题要丢，否则过滤强度不一致会抬高在它上面测出的指标。
> 详见 [16](16-rl-任务集与泄漏过滤.md)。

### Q11：奖励函数怎么设计的？塑形项怎么加？

> 参考思路：结果奖励用精确匹配不用 LLM judge（确定、免费、不漂移），F1 只报告不训练
> （部分给分鼓励对冲）。**重点讲塑形必须门控在正确性之后**：稀疏奖励下 1.5B 早期
> outcome 恒为 0，效率惩罚就成了唯一有梯度的项，而最省力的最大化办法是「立刻空答」，
> 策略会飞快学会放弃且不可逆。再讲反作弊命中即**作废**而不是打折
> （打折时只要 outcome 比折扣大就仍然有利可图），最有力的一条是编号出处校验。
> 详见 [17](17-rl-奖励与验证器.md)。

### Q12：多轮场景下 loss mask 怎么算？踩过什么坑？

> 参考思路：这是最该主动展开的一题。三个具体的坑：
> ① `derive_messages` 交出的 `arguments` 是**原始 JSON 字符串**，而 Qwen 模板里是
> `| tojson`，对字符串做 tojson 会双重编码；vLLM 服务端会先归一化，
> 所以 rollout 和本地重建每次工具调用都差若干 token，**不报错**。
> ② 停止符 `<|im_end|>` 必须进 mask，否则模型学会永不停止。
> ③ 我一开始断言「每个消息边界前缀都稳定」，六条真实轨迹全失败——
> 原因是 Qwen 把连续 tool 响应合并进一个块，中间前缀确实会移动；
> 真正需要的是更弱的条件「每个 assistant 轮的 prompt 是完整序列的前缀」。
> 解法是让服务端彻底不碰模板：本地套入库的模板、传 token id 给 `/v1/completions`、
> 自己解析工具调用——不一致从「要小心」变成「结构上不可能」。
> 顺带一个数字：**可训练 token 只占 7–12%**。
> 详见 [18](18-rl-分词对齐与loss-mask.md)。

### Q13：为什么用 GRPO？token 级归一化和按序列平均有什么区别？

> 参考思路：GRPO 用同题 G 条 rollout 的均值当基线，省掉 critic。
> 归一化那一问**直接给数字**：一条 5 token（advantage +1）加一条 1 token（advantage −1），
> token 级是 `-0.667`，按序列平均是 `+0.000`（恰好抵消）。多轮场景下这个偏差是系统性的，
> 一直在低估长轨迹，而长程行为正是要训练的东西。
> 再补 `logp_old` 必须采样时记录——事后重算得到的是当前策略的数字，
> ratio 恒为 1、裁剪静默失效，而现象看起来像「训练很稳」。
> 详见 [19](19-rl-GRPO与训练循环.md)。

### Q14：怎么知道一次 GRPO 训练是健康的？

> 参考思路：**先说 reward 曲线单独看不出来**，然后给那张指标表。
> 最重要的是 `all_zero_groups`——组内奖励全相同时 advantage 精确为 0、梯度精确为 0，
> 但照样花掉 G 条完整 rollout，而**损失函数里一切正常**。
> 然后讲 `gave_up` 和 `voided` 这两个对本环境最要紧的：它们**可以和平均 reward 同时上升**，
> 分别对应奖励崩塌和 reward hacking。
> 再讲冷启动 SFT 不是可选项（全零组 ⇒ 零梯度）以及它顺便是 mask 的金丝雀。

### Q15：rollout 的吞吐怎么优化的？

> 参考思路：先给实测的长尾数字 **p50=9s、p95=236s**，说明多轮 Agent rollout
> 长度天然差一个数量级。批同步调度的上界是每批最慢那条，于是大部分时间并发都在空转；
> 连续补位是一个信号量加三十行。**关键是我把批同步也留在代码里**（`--schedule batch`），
> 专门用来产出对照数字——这样有的是「优化前后」，而不是「我认为这样更好」。
> 再补两个能直接对应行动的指标：`slowest_5pct_share` 和 `utilisation`（并发占用率），
> 以及零成本的前缀缓存优化（同题 G 份刻意相邻）。
> 详见 [20](20-rl-Rollout引擎与系统指标.md)。

### Q16：你这个项目有哪些地方是没做完的？

> 参考思路：**这题要老实答，而且老实答是加分的**。照实说：环境、数据、奖励、分词对齐、
> GRPO 目标函数、训练循环编排都已验证，正式训练与消融实验待 GPU；
> `rl_check` 20 个阶段全绿但其中训练那几个是 stub hooks 跑的编排逻辑，
> 不是真实的 forward/backward。
> 然后说清楚**为什么按这个顺序**：分词对齐是唯一一种「看起来在训练、其实在学噪声」的
> 失败模式，所以它必须在 Pi 上先绿再租卡；不需要 GPU 的事全部做完，租卡后只做已调通的实验。
> 这比含糊说「训练还在跑」要好得多。

## 14.6 最后的建议

- **不要试图记住所有细节**，挑 3～4 个你觉得最能体现深度的点，准备到能画图、能举反例的程度。
  - 投 **Agent / 应用** 方向建议挑：`step/end` 在 `tool/approval` 之后发出的顺序细节、
    子代理严格审批策略解决的死锁问题、真实 token 数驱动压缩触发、
    `contained_path()` 里 `startswith` 边界条件的坑。
  - 投 **Post-Train / RL** 方向建议挑：arXiv→HotpotQA 的实测推翻、
    `arguments | tojson` 双重编码、塑形门控在正确性之后、token 级 vs 按序列归一化的那两个数字。
- **RL 这部分的每一章都刻意把「错法」写在「对法」旁边**，因为面试官真正在考的是
  「你知不知道不这样做会怎么错」。能说出失败机制，比能说出正确做法更有说服力。
- 被问到不知道/记不清的细节时，**诚实说"这个我记不太清具体实现，但设计意图应该是
  XXX"**，比硬编一个错误答案要好得多——特别是对着一个懂这个方向的面试官,编造细节
  很容易被追问戳破。
- 如果时间允许，建议真的跑一遍这两个：
  - `cd backend && python ../tools/harness_probe.py` —— 看一遍完整事件序列长什么样，
    比只看代码更容易在面试时脱口而出事件类型名和顺序。
  - `python -m rl.checks.rl_check --offline` —— 20 个阶段的输出本身就是一份
    「我验证了哪些不变量」的清单，每一行都能展开成一个追问的答案。

祝面试顺利。
