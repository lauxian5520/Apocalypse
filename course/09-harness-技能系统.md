# 09 · 技能系统（Skills）

## 9.1 要解决的问题：过程性知识放哪里

Agent 经常需要"知道怎么做某件复杂的事"——比如"怎么把 Markdown 转成排版精美的 Word 文档"，
这类知识往往是一长段流程说明（先做什么、注意什么坑、用什么脚本、最后怎么验证结果），
不适合塞进短小精悍的工具描述，也不适合一股脑写进系统提示词（那样每次对话都要为一个可能
根本用不上的流程支付额外的 token 成本，还会稀释真正相关的上下文）。

> **严谨定义**：这类"怎么做一件事的流程性知识"，在 Anthropic 等公司近年的 Agent 产品设计里
> 被称为 **Skill（技能）**——一份可以被模型按需读取、指导它完成特定任务的自然语言文档，
> 通常配合可选的辅助脚本/参考资料，区别于"工具"（工具是一个可以被直接调用执行的函数接口）。
>
> **大白话**：工具是"能力"（我能读文件、能跑命令），技能是"说明书"（用这些能力具体怎么
> 拼出一份 Word 文档，中间要注意哪些坑）。有能力不代表知道怎么高质量地完成一件具体任务——
> 这正是技能系统存在的意义。

## 9.2 系统提示词里只放"目录"，正文按需读取

```markdown
---
description: 一句话说明这份流程是干什么的
keywords: 逗号, 分隔, 可选
---

正文……（可能很长）
```

系统提示词里，对每个技能**只注入名字和这一句 `description`**（`catalogue()` 函数生成的
目录），模型判断"这个任务可能需要这份技能"时，自己主动调用 `load_skill` 工具，把正文
读进当前对话。

### 为什么不做"关键词自动匹配、命中就自动注入"

这是一个**主动设计取舍**，`harness/skills/registry.py` 的模块文档字符串里专门写了理由，
直接呼应 [04](04-harness-总览与两大设计原则.md) 讲的核心不变量——"模型看到的一切必须先
写进日志"：

> 如果做成"关键词命中就自动把正文塞进系统提示词"，这份正文的注入行为发生在系统提示词
> 拼装阶段，**根本不会经过 `emit()` 写进事件日志**——那就会出现"模型确实看到了这段内容，
> 但事件日志里压根找不到它是什么时候、因为什么被注入进去的"，直接违反了"全链路可追溯"
> 这条不变量。

而现在的实现——正文只能通过调用 `load_skill` 工具获取——这次读取动作本身，作为一次
**普通的 `tool/call` + `tool/result`**，天然就会被记进日志，重放时一字不差。**这是一个
很典型的"为了保住一个核心系统不变量，主动放弃了一个看起来更'智能'、更省事的功能"的例子**，
值得在面试里当作"架构一致性优先于局部便利性"的具体案例讲出来。

## 9.3 两种形态：单文件技能 vs 技能包

```
data/skills/web-research.md          ← 纯流程文档，一个文件就是一个技能
data/skills/pptx/                    ← 技能包
  SKILL.md                           #   入口，格式同上
  scripts/build_deck.py              #   附带脚本
  references/                        #   参考资料（可选）
```

技能名就是文件名（或目录名）——**没有单独的 `name` 字段**，避免"文件名和声明的名字对不上"
这种自相矛盾的状态。Frontmatter 是手写的极简 `---` 分隔解析器（不是引入一个完整的 YAML库），
只认 `description`（必填）和 `keywords`（可选，逗号或中文顿号分隔）。

### 技能包的文件怎么"进场"

调用 `load_skill` 时，如果这是一个技能包（带 `scripts/`/`references/` 的形态），
它的附带文件会被**复制**进当前会话工作区的 `.skills/<名字>/` 目录下。

> **为什么是复制，而不是让沙箱直接访问 `data/skills/` 目录**：[08](08-harness-沙箱与安全边界.md)
> 讲过，沙箱的路径收敛逻辑（`Workspace.resolve()`）只承认工作区内部的路径——这是整个系统
> 安全边界最核心的一条假设。如果为了让某个脚本能跑起来，就单独给沙箱开一个"能访问
> `data/skills/` 目录"的口子，等于在这条核心假设上开了个例外——例外一多，安全边界就
> 变得难以推理。反过来，"把文件搬进工作区"这个操作发生在**工具执行阶段**（`load_skill`
> handler 内部），而不是修改沙箱本身的访问规则，付出的代价只是"多复制一次文件"，
> 换来的是"沙箱的核心规则从头到尾只有一种"。

复制逻辑（`install()`）还处理了几个细节：跳过 `__pycache__`/`.git`/`node_modules` 等
目录、跳过任何点号开头的路径、限制单个技能包总大小不超过 8MB、写入前调用工作区自己的
`check_quota()`。目标目录 `.skills/` 本身以点号开头，是为了在 `glob`/文件列表里默认不
显眼地出现，同时前端"文件"页签会单独把 `.skills/` 下的文件标记为"技能附带脚本"，
和 Agent 自己真正生成的产出文件分组展示。

之后模型就能在 `bash` 工具里跑这个脚本：

```bash
python3 .skills/pptx/scripts/build_deck.py 大纲.md 输出.pptx
```

## 9.4 容错策略：技能坏了 vs 工具坏了，处理方式完全不同

这一点在 [07](07-harness-工具系统与审批.md) 已经埋过一个对照，这里正式展开：

| | 工具契约损坏（`.json` 没有对应 `.py`） | 技能文件损坏（缺 description、frontmatter 没闭合） |
|---|---|---|
| 处理方式 | **立即 `raise`，应用启动直接失败** | **跳过这一份，记进 `issues` 列表** |
| 通过什么暴露 | 部署日志/启动异常 | `GET /harness/skills` 接口返回，前端插件面板标红 |
| 为什么不同 | 这是"仓库打包错误"——代码和配置本该在同一次代码提交里保持一致，
    不一致意味着一次真实的开发失误，理应在部署那一刻就被拦下来。 | 技能文件被设计成
    "运行时可以随意增删改、不需要重启"的内容，某个人手写 frontmatter 时少打一个 `---`
    是完全可能发生的日常小失误，不该让这种失误直接拖垮整个 Agent 服务——其他所有正常的
    工具、正常的技能应该照常可用。 |

> **面试话术**：这是"对错误的严重程度做分级处理"的一个好例子——不是所有校验失败都该用
> 同一种响应方式（一律抛异常，或者一律吞掉打日志）。要看这个错误来自"本该被质量流程
> 挡住的开发失误"，还是"运行时内容天生就允许被随意改动、随时可能出错的用户输入"。

## 9.5 技能不缓存，热更新

和工具注册表的 `load_specs()`/`load_preset()`（都套了 `@lru_cache()`，改了要重启才生效）
形成鲜明对比——技能扫描逻辑**每次调用都重新扫一次目录**，没有缓存。代价是"每次都要重新
读一遍这些小文件"，但收益是**改一份技能文档、加一份新技能，下一轮对话立刻生效，不用重启
整个后端服务**。这个取舍成立的前提是：技能文件数量不多、单个文件不大（`MAX_SKILL_BYTES`
限制到 32KB），重新扫描的开销小到可以忽略不计。

## 9.6 案例：docx / pptx 两个技能包

这两个是仓库里唯一自带脚本的"技能包"形态样例，都遵循同一套流程：

1. Agent 用 `write` 工具写一份 Markdown 源文件；
2. 调 `bash` 跑对应的构建脚本（`build_docx.py`/`build_deck.py`），生成 `.docx`/`.pptx`；
3. **强制要求读回**：调 `read_docx.py`（基于 pandoc）/`read_pptx.py`，把生成结果重新
   解析成文本打印出来，供模型核对内容是否符合预期。

### 为什么必须"读回"，`read` 工具不能直接看

`.docx`/`.pptx` 本质上是一个 ZIP 压缩包，里面装的是若干个 XML 文件——通用的 `read` 工具
只会把它当成二进制/纯文本源码读出来一堆乱码，完全没法验证"生成的文档内容对不对、
排版有没有问题"。README 原话很好地总结了这个动机：

> "两个技能的 `SKILL.md` 都要求生成后必须读回核对再回话——否则'已生成'只是它的一厢情愿。"

> **大白话**：一个脚本的退出码是 0（没报错），不代表它生成的文件真的符合预期——万一
> Markdown 里某个表格语法写错了，脚本可能"成功"跑完，但生成的表格是空的或者错位的。
> 靠"专门写一个读回脚本，把生成结果转译回文本，让模型（或者人）能实际检视内容"，
> 才是真正验证"这件事做成了"的方式，而不是仅仅相信程序执行没报错这个弱信号。

`pptx` 技能还多了一步可选的 `thumbnail.py`（依赖 LibreOffice + `pdftoppm`，只在开发机
上可用，Docker 镜像里没装这两个二进制），能把每一页幻灯片渲染成 PNG 缩略图——这一步
同时还起到了"验证文件真的能被 Office 软件正常打开"的作用，比单纯"文本解析成功"多一层
保证。

## 9.7 第三方技能包的许可证坑（一个很好的合规意识案例）

CLAUDE.md 里专门有一段警告：`anthropics/skills` 仓库公开的 docx/pptx 技能虽然代码可读，
但附带的 `LICENSE.txt` 明确禁止"在 Anthropic 的 Services 之外保留副本""复制""制作衍生
作品"——**不能直接搬进自建服务器使用**。这个项目里的 docx/pptx 是**独立实现**，只依赖
`python-docx`/`python-pptx`/`pandoc` 这些本身开源的库，从零重新写的功能等价物，
不是对官方仓库代码的移植或修改。

> **面试话术**：这是一个体现"工程判断力不止是技术选择，也包括合规意识"的细节——发现一份
> 现成的、公开可读的代码不代表可以直接拿来用，License 条款也是工程决策的一部分输入。
> 面试官问到"你怎么处理第三方代码依赖"这类问题时，这是一个具体、真实、可核实的例子。

## 9.8 本章小结

- Skills 解决"过程性知识怎么存放"的问题：系统提示词只带目录（省 token），正文靠
  `load_skill` 工具按需读取（保住"全链路可追溯"这条核心不变量）。
- 单文件技能和"带脚本的技能包"是两种形态，后者的附带文件会被复制进会话工作区，
  而不是放宽沙箱本身的访问规则。
- 技能损坏和工具契约损坏走两条完全不同的容错路径，背后是对"错误来源"的分级判断。
- 技能不缓存，改完立刻生效；这是和工具注册表（重启才生效）刻意做出的不同权衡。

这个系统怎么控制风险和花费。
