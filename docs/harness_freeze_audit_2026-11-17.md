# Harness 工作台卡死审核

审核日期：2026-11-17。代码基线：`e259357`，同时检查当前工作区。用户确认的症状是“整个网页都无法点击或滚动”。

## 结论与证据边界

最高优先级原因是前端流式渲染导致浏览器主线程长时间繁忙：**逐片段重写增长中的回复、追加事件 DOM，然后同步读取 scrollHeight 强制布局**。本地隔离测试已复现该路径导致几十秒不响应，并通过单变量对照定位到逐片段滚动触发的布局开销。

这不是线上故障现场采样：没有连接生产服务器，也没有取得生产浏览器 Performance trace、实际部署版本、服务器资源或日志。下面区分了已复现的问题与代码检查发现的风险。没有修改业务源码、运行中的服务或部署配置。

## 1. P1：每个输出片段触发布局，足以冻结整个页面【已复现】

代码位置：

- `frontend/js/pages/harness.js:303`：每次 onEvent 都立即操作页面。
- `frontend/js/pages/harness.js:311`：累加文本后把整个 streamed 字符串重新赋给 pre.textContent。
- `frontend/js/pages/harness.js:329`：每个事件都调用 appendEvents。
- `frontend/js/pages/harness.js:332`、`:267`：立即执行 scrollDown，读取 scrollHeight 后写入 scrollTop。
- `frontend/js/pages/harness-stream.js:55`：一次读取到的全部 SSE 行在同一轮循环中逐条处理，没有时间预算或主动让出主线程。

写 DOM 会使布局失效，紧接着读取几何信息可能强制浏览器立刻计算布局。长文本在每次更新后重新换行，事件面板也持续增长；多个片段连在一起处理时，点击、计时器和绘制没有足够执行机会。代码已有增量追加事件的修复，确实避免了每个片段全量重建事件列表，但没有消除上述布局链路。

### 本地隔离实验

Windows，Headless Microsoft Edge 157.0.4341.60，1600×900；使用项目实际 harness HTML、CSS、utils、split-pane 和三个 harness 脚本。用模拟身份与接口替代服务器，关闭装饰背景、精灵和音乐脚本。每个正文片段为 16 个 ASCII 字符。完整事件序列为 user/message、turn/start、N 个 assistant/chunk、最终 assistant/message、turn/end。

下表模拟网络或页面处理积压后，多个 SSE 事件集中可读。每个场景为单次测量，没有 CPU 降速；数值用于定位机制，不能解释为生产延迟分布。布局数据来自 Chromium Performance.getMetrics；零延时定时器用于测量主线程迟迟无法调度的时间。

| 场景 | 片段数 | 流消费到详情请求 | 零延时定时器延迟 | 布局耗时 | 布局次数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 当前代码，默认事件面板 | 1,000 | 1.56 秒 | 1.58 秒 | 1.43 秒 | 1,005 |
| 当前代码，默认事件面板 | 2,000 | 13.79 秒 | 13.84 秒 | 12.66 秒 | 2,005 |
| 当前代码，默认事件面板 | 4,000 | 63.22 秒 | 63.37 秒 | 59.08 秒 | 4,005 |
| 测试副本仅去掉 onEvent 中的 scrollDown | 4,000 | 0.158 秒 | 0.339 秒 | 0.121 秒 | 1 |
| 当前代码，改看插件面板 | 4,000 | 35.31 秒 | 35.32 秒 | 33.61 秒 | 4,003 |

原始结果：`data/audit/harness_frontend_probe.json`。测试副本通过请求拦截在内存中修改，不改磁盘上的 harness.js。部分长任务观察记录为空，因此不把该字段当作“没有阻塞”的依据；这里采用独立的定时器延迟和浏览器布局计数。

4,000 片段场景产生约 20,119 个 DOM 元素。关闭事件面板只能减轻负担，增长中的正文反复布局仍足以造成长时间不响应。删除滚动调用是诊断对照，不能作为完整修复直接交付。

补充高吞吐分批流测试：每 150ms 送入 32 个片段，共 2,048 个片段，使用未修改的前端代码。整轮约 16.0 秒，记录到 54 次长任务，最长 659ms，计时器最大间隔约 695ms；累计布局约 11.92 秒、2,053 次。这个到达速率是测试输入，不是生产模型实测速率；它表明即便没有一次性送入全部事件，逐片段布局仍会产生明显的反复卡顿。原始结果：`data/audit/harness_paced_probe.json`。

建议修复：

1. onEvent 优先更新数据与待渲染队列；用 requestAnimationFrame 合并更新，每帧最多刷新一次正文、事件列表与滚动位置。不能给每个事件分别注册一个 rAF。
2. 为解析和渲染都设置小的执行时间预算，例如先以每批 4–8ms 为目标，超过预算就让出主线程。仅在最终滚动处加 rAF，仍不能解决巨大积压包的同步解析与全量 DOM 创建。
3. 缓存正在输出的文本节点，合并片段后更新，避免逐片段重写完整文本。只有正文变化才更新正文；reasoning-only 片段不要触发空正文更新与滚动。
4. 只在用户原本接近底部时自动跟随；批量更新后最多读取一次 scrollHeight。用户向上阅读时暂停跟随。
5. 同步实施下一节的列表上限；否则单帧即使只绘制一次，十万条记录仍可能形成长任务。

## 2. P1：历史与原始事件没有分页或展示上限【代码确认】

代码位置：`harness.js:75`、`:120`、`:385`；`harness-trajectory.js:102`、`:121`；`backend/routers/harness.py:99`；`backend/harness/session/sqlite_store.py:87`。

打开会话会获取全部事件，原始事件标签页直接 events.map(...).join('') 后一次写入 innerHTML；流式期间每个 assistant/chunk 都成为一行且永不移除。重新打开、刷新后任务结束、切回事件标签都可能再次全量渲染。后端虽然支持 after 游标，但没有 limit，前端也没有用它恢复增量。

上下文压缩只影响发给模型的消息；`backend/harness/session/compaction.py` 明确保留原始事件，因此不会让浏览器历史变小。`findCall` 为每个工具结果倒序扫描整个历史，也会增加工具密集型会话重建成本。

建议修复：

- 默认显示消息、工具状态和最近 200–500 条事件；chunk 默认合并为当前输出记录或不进入常驻事件列表。完整原始日志仍保留在服务端。
- 后端增加有上限的分页接口，支持历史向前翻页、after 增量补齐；初次打开先获取最近的完整消息，不能只取最近若干原始 chunk 后误认为已有完整对话。
- 已结束回复用最终 assistant/message 展示，原始分片按需加载；仍在运行的回复保留可恢复的文本快照或可补齐的分片位置。
- 大工具结果先显示预览，展开再取完整内容；调用关联建立 Map，避免每张工具卡片反复遍历全历史。

## 3. P1：后端异步执行链包含同步数据库与文件操作【代码确认，未做生产压测】

代码位置：`backend/harness/loop/agent.py:152`、`:173`、`:200`；`backend/harness/context.py:59`；`backend/harness/session/sqlite_store.py:43`、`:75`、`:87`；`backend/harness/tools/builtin/fs.py:21`、`:83`、`:107`。

Agent 的 async 执行链直接调用同步 SQLAlchemy read/commit。文件工具虽然声明 async def，内部却同步读取、遍历、写入文件，grep 还直接执行正则匹配。慢磁盘、数据库锁等待、大历史或大量文件会阻塞所在事件循环。Dockerfile 默认只有一个 Uvicorn 进程，因此这些操作可能拖慢多个用户的 API/SSE。

已有 WAL 和每 32 个片段或 150ms 批量提交，可以减少事务次数，但不能让同步数据库操作自动变成异步。普通 def 路由由 FastAPI 放进线程池，与 async 任务中直接调用同步工具函数是两回事。

另外，`manager.py:357` 的 usage_summary 为统计少量 llm/usage，读取父会话和所有子会话的全部事件；前端恢复运行状态时每两秒请求的详情接口又会调用它，长会话会放大数据库读取、JSON 解析与内存压力。

建议修复：

- 用有界线程池承接完整同步数据库操作和文件 I/O，在线程内创建、使用、关闭数据库 Session；同一会话写入仍保持顺序，不能通过并发提交打乱事件。
- 限定目录遍历、文件大小和匹配耗时；可能长时间占用 CPU 的搜索放入可超时终止的独立进程，不能认为 to_thread 就能可靠终止正则执行。
- usage 在 SQL 中按事件类型过滤或维护轻量累计值；状态轮询使用只返回状态和 last_seq 的轻量接口。
- 增加每用户与全局任务并发上限，避免不同会话无限创建后台任务。根据实际内存和模型接口额度确定数值。

不要直接把 --workers 改成 4 当作修复。`_turn_tasks`、`_active_turns` 和 interrupt tokens 都是进程内状态，且每个进程启动时 reset_running_sessions 会重置数据库中运行状态。多进程前需要处理共享任务所有权、互斥、中断路由和存活租约。

## 4. P2：中断与恢复不够及时，可能让冻结之后仍感觉“停不下来”【代码确认】

代码位置：`backend/harness/loop/interrupt.py`；`agent.py:190`；`tools/builtin/subagent.py:88`；`routers/harness.py:148`、`:223`；`frontend/js/pages/harness.js:342`；`frontend/js/pages/harness-stream.js:16`、`:56`。

- 中断只设置标志。模型流要等下一次产出正文或 reasoning 后才检查；正在执行的工具不会立即被取消。子代理的 deadline 同样在拿到下一个事件后才检查，不是独立计时器。
- HTTPX 配置的 300 秒主要是网络读写等阶段的超时，其中 read timeout 是相邻数据块间的等待上限，并不等于整个任务 300 秒硬截止。持续收到上游数据但没有可下发内容时仍可能长时间等待。
- 新会话先等待自动标题请求，再开始 run_turn；标题阶段还没有创建 interrupt token，首条正文可能额外等待一个模型请求。
- 下行 SSE 没有心跳，前端没有取消控制器、闲置超时或自动续读。流断开后 finally 无条件 setRunning(false)，即使详情返回 running 也未调用 adoptRunning，可能让用户误以为任务已停。

建议修复：建立独立的整体 deadline 和中断等待，将模型读取、工具等待与取消信号并行等待；取消时可靠关闭上游连接，清理子进程并写入终止状态。每 10–15 秒发送 SSE 注释心跳；连接丢失后按最后 seq 补齐事件、读取真实状态。自动标题使用短超时或移出首条回复的关键路径。

前端 AbortController 只取消页面订阅，不应被当作服务器任务已停止的证据。服务端继续执行或主动停止需有明确状态协议。

## 5. P2：切换会话时，旧流仍写共享页面状态【代码确认】

代码位置：`frontend/js/pages/harness.js:53`、`:75`、`:287`、`:304`、`:309`、`:341`。

运行时仍可切换会话。openSession 替换 state.sessionId、state.events 并重建对话；旧流的 onEvent 却继续写同一个 state.events，并使用原 typing 节点 insertBefore。旧节点被移除后可能抛 NotFoundError，或者把 A 会话事件混入 B 会话；中断按钮又以当前 sessionId 发请求，可能控制错误目标。

建议修复：为每次加载和流订阅绑定固定 sessionId 与 generation；只有匹配当前视图才能更新 DOM。切换时取消旧订阅并清理它的待渲染批次，服务器任务是否继续运行独立管理。所有异步 finally、轮询和详情返回也校验身份，避免旧请求覆盖新页面。

## 6. P2：启用 shell 后，输出上限实际上没有限制收集阶段的内存【条件性风险】

代码位置：`backend/harness/sandbox/local.py:80`、`:89`；`docker-compose.yml`。

先 communicate() 把 stdout/stderr 全部收进内存，结束后才按 32KB 截断。子进程持续打印时，父进程可积累大量内存；子进程的 RLIMIT_AS 不限制父进程输出缓冲。当前代码也没有在 CancelledError 路径中可靠杀死并回收进程组。Compose 有 pids_limit，但没有显式 CPU/内存上限。

生产覆盖配置默认关闭 shell，因此不能据此认定本次故障由 shell 引起。若实际开启，应并发持续读取 stdout/stderr、只保留有界缓冲并继续排空或主动终止超限进程；取消与超时都清理进程组。容器资源上限按服务器实际配置设定，并限制并发 shell 数。

## 实施顺序与验收

1. 首个修复：合并流式 UI 更新、消除逐片段强制布局、限制常驻事件行；这是与用户所述症状最一致且已有实验依据的部分。
2. 第二个修复：历史分页与增量恢复、会话切换隔离、断线后运行状态同步。
3. 第三个修复：隔离同步 I/O、精简 usage 查询、增加全局并发上限、完善取消清理。先保持单进程，再按实际容量决定是否调整部署架构。

建议验收场景与目标（这些是拟定标准，尚未实现或验收）：

- 10,000 个累计片段、50,000 条历史、长工具结果、慢上游、网络中断、生成中切换会话、多个用户同时调用。
- 页面可以持续输入、点击中断和手动滚动；代表性设备上交互延迟目标低于 200ms，无秒级长任务。长期 DOM 数量不随累计 chunk 无限增长。
- 合并批次不丢字、不乱序；最终消息、工具调用、审批与原始持久化事件对应；恢复时按 seq 去重补齐。
- 中断在预设时限内结束可取消任务，子进程已退出；后端繁忙时 healthz/readyz 仍及时响应。
- 既有 browser_check.py 覆盖基础发送、刷新恢复、中断，但未覆盖数千片段、长历史和渲染时间预算；应补上述有意义的性能回归场景。

上线核实可在一次真实复现时同时保存：浏览器 Performance trace（重点看 Layout、Recalculate Style、文本布局和脚本长任务）、同一时段的 API 延迟、后端 CPU/RSS、容器 OOMKilled 状态，以及实际运行版本。若浏览器冻结期间 API 仍及时响应，优先验证前端修复；若所有用户 API 同时变慢，再定位同步 I/O 或资源竞争。

仓库中的 Nginx 配置已经设置 proxy_buffering off，SSE 响应也有 X-Accel-Buffering: no；不能把“再关闭一次 Nginx 缓冲”作为当前代码问题的主要解决办法。若实际还有 CDN、网关或不同的生产配置，需要另行核实它们的缓冲行为。

临时措施是缩短单次长回复、避免一个会话持续累积大量历史、适当减少后台装饰动画。切换到插件面板只能缓解，实验已显示不能根治；增加代理超时时间、重启服务或升级服务器也不能消除浏览器中的逐片段布局。
